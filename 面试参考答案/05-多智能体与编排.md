# 五、多智能体与编排（参考答案）

**Q83.【P1】 多 agent 拓扑有哪些？**
一句话：四种主流：① Orchestrator-Worker（一个主管拆解分派、汇总结果）——最通用；② 流水线（A→B→C 串行接力）——阶段清晰的流程（解析→生成→审核）；③ 辩论/评审（生成者 + 批评者互搏）——质量要求高、有客观判据的任务；④ 群聊/swarm（自由移交控制权）——灵活但难控，生产慎用。

展开：用公司组织来类比这四种拓扑最直观：

| 拓扑 | 类比 | 适用 |
|---|---|---|
| Orchestrator-Worker | 经理拆任务给下属，收报告 | 大多数复杂任务（研究、重构） |
| 流水线 | 工厂流水线，每站只干一件事 | 阶段固定的流程：解析→生成→审核 |
| 辩论/评审 | 作者 + 审稿人 | 有客观判据的高质量要求任务 |
| 群聊/swarm | 没有经理的创业团队，谁顶上谁干 | 探索性任务，生产慎用 |

选型口诀：能流水线不编排，能编排不群聊——**控制流越显式越好治理**。想象排查一次失败：流水线里你一眼知道卡在哪一站，群聊里你可能翻几十条消息才搞清谁把任务带偏了。orchestrator 的三个关键设计：任务拆解粒度（拆多细）、结果验收标准（worker 交付怎么判合格）、失败重派策略（不合格打回还是换人）。

陷阱：没人一开始就该上多 agent。加分点：说"拓扑是演化的——先单 agent，测出瓶颈（上下文装不下/单点太慢）再拆"，这句话能直接体现生产经验。

**Q84.【P1】 什么时候拆多 agent？拆错的代价？**
一句话：拆的真实理由只有三个：① 上下文装不下（每个子任务需要各自的大量专属上下文）；② 需要并行提速（独立子任务 fan-out）；③ 需要不同的"专业配置"（不同模型/不同工具集/不同 system prompt，避免互相干扰）。其他理由（"看起来高级"）都是伪需求。拆错的代价：成本×N、延迟可能反升（协调开销）、错误传播链变长、评测归因困难。

展开：判断标准很朴素——**单 agent + 好工具能解决的就别拆**。多 agent 用工程复杂度换来的只有两样东西：上下文隔离和并行度（详见 Q85、Q92），别的东西（"更强的智能""更好的推理"）拆 agent 本身不提供。

三个真实理由各配一个例子：

1. 上下文装不下：研究类任务要读 50 个网页，读的过程就把窗口塞满了，主 agent 没空间思考和写报告 → 拆出子 agent 各读各的，只交回摘要；
2. 并行提速：对 10 个竞品分别做分析，互相独立 → fan-out 10 个子 agent 同时跑，墙钟时间约等于最慢的那个；
3. 专业配置：写代码要低 temperature + 代码工具集，写文案要高 temperature + 搜索工具，两套配置塞进一个 agent 会互相干扰 → 各配各的。

反面信号：子任务间高频互相依赖、需要共享大量中间状态 → 拆了反而更慢，因为协调成本吃掉了并行收益（连 Q92）。

陷阱：这题的正确姿势是给出"拆的前置检查清单"，而不是背模式。面试官追问"你的项目为什么拆了/没拆"时要能落到具体瓶颈上。

**Q85.【P2】 Sub-agent 上下文隔离？**
一句话：主 agent 给子 agent 一段任务描述 + 必要材料，子 agent 在自己的独立上下文里跑完（查 20 个网页、翻 10 个文件），只把**结论摘要**交回主 agent——过程的海量中间信息不污染主上下文。

展开：这是多 agent 存在的最硬理由，理解它要从"上下文是稀缺资源"出发。

为什么重要——先看数字：主 agent 自己去查 20 个网页，每个网页正文约 3k token，60k token 的原始内容直接灌进主上下文：窗口逼近上限、费用暴涨、注意力被稀释（模型要在 6 万 token 里找重点，质量下降，见 lost in the middle）。隔离后：20 个子 agent 各自在 5k 的独立上下文里读完、消化，每个只交回 200 字结论——主上下文只增加 4k token，却拿到了全部结论。

类比：管理者不读下属的所有原始邮件，只读报告。经理的价值在于掌握全局，而不是亲历每个细节。

代价与对策：信息有损——子 agent 不知道哪些细节对全局关键（它看不到主 agent 的目标全貌）。所以任务描述里必须写清"汇报应包含什么"（关键数字、来源链接、置信度、失败原因），等于给报告定了模板。

陷阱：面试官可能反问"摘要丢了细节怎么办"——答：按需二次下钻（orchestrator 对可疑结论派子 agent 复查特定细节），而不是把所有原始数据常驻主上下文。

**Q86.【P2】 DAG 并行执行怎么处理？**
一句话：把计划表示为任务图（节点=子任务，边=依赖），入度为 0 的任务并发跑，完成的任务解锁后继节点；汇总节点等待所有前驱完成。要点：依赖声明要显式、失败传播策略明确（上游挂了下游跳过还是重试）、设全局超时。

展开：先建立直觉：DAG 就是一张"先做什么后做什么"的施工图。比如"竞品调研报告"：

```
查公司A资料 ──┐
查公司B资料 ──┼──→ 汇总对比 ──→ 写报告
抓行业数据 ──┘
```

三个资料任务互不依赖（入度 0）→ 并发跑；汇总必须等三者全到。执行器逻辑就四步：

1. 找出所有入度为 0 的节点，提交执行；
2. 某节点完成 → 它指向的后继节点入度减 1；
3. 入度变 0 的后继节点提交执行（这就是"解锁"）；
4. 重复直到全部完成或触发失败/超时策略。

实现不必造轮子：图编排框架（LangGraph 的 send/并行分支）或任务队列（Celery/Temporal 思想）都有现成原语。

关键坑：① **隐式依赖**——子任务 B 实际需要 A 的结果但图里没画边，B 拿着过时/空输入跑完了，结果错误但"成功"——靠评测和 trace 回放补图；② **汇总的信息压缩**——10 个子结果直接进主上下文会撑爆窗口，先各自摘要再进。加分点：DAG 适合"可静态分解"的任务；分解本身动态的场景（查着查着才知道还要查什么，DAG 画不出来的）用 orchestrator 动态派发更合适。

**Q87.【P2】 A2A 和 MCP 的分工？**
一句话：MCP 连接"agent ↔ 工具/资源"（垂直集成：能力供给）；A2A（Agent-to-Agent，Google 发起）连接"agent ↔ agent"（水平协作：不同团队/公司建的 agent 互相委托任务、交换进度）。一个管"我有什么工具"，一个管"我怎么和同行 agent 合作"。

展开：用一个具体场景把分工讲透：你的差旅 agent 帮你订机票。

- 差旅 agent 用 **MCP** 连接自己的工具：日历 MCP 读你的行程、支付 MCP 付款、文件 MCP 读护照扫描件——这些都是"自己人"，能力供给关系；
- 订票环节它去调用航司的订票 agent——那是另一家公司建的、有自己的内部工具和权限体系，你不可能要求它把订票能力做成你的 MCP 工具。双方用 **A2A** 对话：你的 agent 读对方的 Agent Card 发现"这家能订票、需要哪些参数"，然后发起委托，对方回报"已锁座→已出票→电子票已发送"。

A2A 两个核心概念：**Agent Card**（agent 的能力自我描述，JSON 格式，供对方发现和判断"能不能把活交给它"）；**任务生命周期**（委托 → 状态回报 → 交付，类似外卖订单从下单到送达的状态流转）。MCP 解决的是"工具接口不统一"，A2A 解决的是"异构 agent 互操作"：发现、鉴权、任务语义。

陷阱：诚实答法——协议层在快速演化、格局未定，死记协议细节没意义；重点是理解问题本身（跨组织 agent 怎么互相发现、信任、协作）。

**Q88.【P1】 多 agent 框架怎么选？自研边界？**
一句话：优先级：① 先试单 agent；② 流程可预期 → 图编排（LangGraph）；③ 需要高度动态、追求控制力 → 自研 orchestrator loop（几百行：模型 + 工具注册 + 消息传递 + 状态存储）；④ 快速原型 → 轻量 handoff 模式（如 OpenAI Swarm 思想：agent 间移交 + 共享上下文）。自研的合理边界：核心 loop 值得自研（你才真正掌控上下文工程和成本），但别自研向量库、评测平台这类通用件。

展开：选型的真实考量三条：**掌控力**（出 bug 时你能不能读框架源码定位问题，还是只能去 GitHub 提 issue 等回复）、**迁移成本**（业务逻辑和框架 API 缠得有多深，换框架要重写多少）、**可观测性集成**（框架的 trace 能不能接进你们现有的监控体系）。

为什么"核心 loop 值得自研、通用件不要"：核心 loop 本质是"调模型 + 执行工具 + 更新状态"的 while 循环，几百行就能写完，自研后上下文工程、成本控制、重试策略全在你手里；而向量库、评测平台是重基建，自研是几个月的活且不会比别人做得好。

加分观点（值得原样记住）："框架的价值在前期快，生产系统的复杂度最终都会穿透框架抽象——所以核心 loop 保持薄、可读、可调试。"

**Q89.【P1】 状态共享：黑板 vs 消息传递？**
一句话：黑板（blackboard，共享工作区）：所有 agent 读写同一份结构化状态——信息透明、易查全局，但会争写、且人人都看到一切（上下文膨胀 + 信息过载）；消息传递：agent 间点对点发摘要——隔离好、职责清，但信息可能滞留、全局视图难拼。实践主流：**共享状态 + 受控读写 + 各 agent 只订阅相关部分**的混合。

展开：这题是分布式系统老问题换了新皮，用微服务类比最省力：黑板 = 多个服务共读共写一个数据库（改一个字段全组都感知，但没人知道别人会不会踩自己）；消息传递 = 服务间 API 调用（边界清晰，但想知道全局状态得把一堆服务的响应拼起来）。

设计核心问题是"谁能看到什么"，两个极端各有病：

1. 全部共享 → 子 agent 的上下文被无关信息污染。比如 10 个并行 worker 共享一块黑板，每个 worker 启动都要把黑板读进上下文——其他 9 个任务的中间状态对它是纯噪音，隔离的意义（Q85）就没了；
2. 完全隔离 → A 和 B 各自搜索后得出矛盾结论，谁也不知道对方的存在，重复劳动 + 结论打架，到汇总才发现。

工程折中：**状态分层**——全局任务目标（人人可见）/ 各子任务工作区（只有该任务相关方可见）/ 结论区（完成的摘要进这里），orchestrator 负责跨层搬运摘要。答出"微服务共享数据库 vs API 通信"这个类比是直接加分项。

**Q90.【P1】 子任务失败怎么传播？**
一句话：失败传播策略按任务关系定：独立子任务 → 失败隔离，继续跑其余，最终报告标注部分失败；下游依赖上游 → 级联取消或用降级结果占位（"该数据暂不可得"）；关键路径失败 → 整体失败并回报卡点。核心：**部分成功必须是可表达的状态**，不能静默当全成功。

展开：三种关系的处理用现实项目类比：组里一个人请假（独立任务）→ 工作重新分配，项目照常推进；上游设计没定稿下游开发没法动（依赖关系）→ 要么等要么用草稿占位先开发；核心引擎做不出来（关键路径）→ 整个项目延期，别硬上。

工程实现三件套：

1. 每个子任务带"重要性"标记（关键/可选）——可选任务失败不阻塞交付，但必须在最终结果里如实声明（"3 项完成，1 项失败：原因是…"）；
2. 下游对上游失败的降级路径——预定义占位（"该数据暂不可得"）比让下游拿到空输入自己瞎编强得多；
3. 汇总时强制对账——计划 N 项 vs 实际成功 M 项，对不上就不允许标"完成"。

最危险的失败模式要记住：**静默降级**——worker 失败了、orchestrator 没察觉，产出一个缺数据的报告却标"完成"，用户基于残缺报告做了决策。这是多 agent 系统里最伤信任的故障，防线就是上面第 1、3 条。

**Q91.【P2】 多 agent 评测难在哪？**
一句话：三个难：① 归因难——端到端失败时不知道是 orchestrator 拆错了、worker 干砸了还是信息传递丢了；② 组合爆炸——agent 配置 × 拓扑 × 任务类型的矩阵跑不完；③ 评测环境更重——要 mock 多个 agent 的行为。解法：组件级评测（单测每个 agent 的职责）+ trace 驱动的失败归因（Q71）+ 小规模端到端回归。

展开：先理解归因难为什么是多 agent 特有的：单 agent 失败，答案就在一条 trace 里；多 agent 失败可能出在三处——**计划层**（orchestrator 把任务拆错了，worker 执行得再好也是错的）、**执行层**（某个 worker 自己干砸了）、**通信层**（worker 干得对，但交接时任务描述有歧义/结论摘要丢了关键信息）。同一种端到端症状，三种病根，药方完全不同。

实操路线（分两层，像软件测试的单元测试 + 集成测试）：

1. **组件级**：给每个 agent 定独立的输入→输出契约，各自配小评测集先达标。研究 worker 单独测"给一个主题，产出摘要的事实准确率"，orchestrator 单独测"给一个目标，产出计划的拆解合理性"；
2. **端到端**：拼装后跑小规模回归集，失败案例用 trace 回放定位到具体 agent 的具体轮次。

加分点：多 agent 有单 agent 没有的失败模式——通信语义（任务描述歧义）、交接遗漏、重复劳动，这些要专门造评测用例，通用评测集覆盖不到。

**Q92.【P1】 多 agent 的成本延迟放大效应？**
一句话：每个 agent 每步都是一次完整 LLM 调用，N 个 agent × M 步 = N×M 倍调用，协调开销（互相等待、重试、开会式讨论）还会加延迟——并行收益经常被协调成本吃掉。控制：限制 agent 数量和轮数预算、子 agent 用小模型、结论而非过程传递（Q85）、并行只在真正独立的任务上用。

展开：先建立数字感——算一笔账：3 个 worker 各跑 10 轮、每轮上下文 5k token = 150k token，这还没算 orchestrator 自己的拆解和汇总调用。多 agent 任务的花费轻松是单 agent 的 5~10 倍。延迟上，"并行"省下的时间经常被"协调"加回去：worker 互相等结果、失败重试、orchestrator 来回派发，排队理论告诉我们等待时间不是简单相加而是超线性增长。

一个犀利的判据：**"并行的物理收益（IO 等待重叠）是否大于协调的逻辑成本？"** 拆 10 个 agent 各干 1 分钟的活，可能不如 1 个 agent 串行 5 分钟——因为前者还要加上排队、失败重试和结果合并的时间。

四个控制手段按性价比排序：

1. 子 agent 用小模型（worker 干的是窄任务，通常不需要旗舰模型，这里能省最多钱）；
2. 结论而非过程传递（Q85，直接砍掉主上下文的 token 量）；
3. 限制预算——agent 数量上限 + 每个子任务轮数上限，超了就强制收敛；
4. 并行只给真正独立的任务（有依赖的强行并行只会增加等待和重试）。

陷阱：答题时主动带数字（比如上面 150k token 那笔账），这是"有生产经验"和"背概念"的分水岭。

**Q93.【P1】 HITL 在多 agent 工作流的插入点？**
一句话：四个经典插入点：① 计划批准后执行前（成本最低的干预点——方向错了这时拦）；② 敏感操作执行前（资金、外发、删除，每个 worker 的敏感工具调用）；③ 阶段交付物验收（worker 的产出经 orchestrator 汇总后人工审再进下一步）；④ 异常升级（失败超限、置信度低）。粒度原则：审批对象是"有风险的决策点"，不是"每个 agent 的每步"。

展开：为什么"计划批准后执行前"是最便宜的干预点——错误在系统里停留越早，纠正成本越低：方向错误的计划如果放行，10 个 worker 会认真地把错误方向执行完，你得到 10 份作废的产出；在计划阶段拦住，只损失一次 orchestrator 调用。这和软件工程"bug 越晚发现修得越贵"是同一条规律。

多 agent 特有的三个工程问题：

1. **并行审批拥堵**：5 个 worker 同时请求审批怎么办 → 审批队列 + 批量确认 UI，别让人一条条点；
2. **审批超时策略**：超时是默认拒绝还是挂起？答案取决于操作风险——资金类默认拒绝（宁可不做），只读类默认放行；
3. **审批人信息不足**：审批人看不到子 agent 的完整上下文，所以审批卡片必须自带决策要素：做什么、为什么、风险、可选项。一张只有"是否继续？[是/否]"的审批卡片等于逼人盲签。

连回 Q65/Q68：每个插入点都需要状态持久化支撑——审批中断几小时后恢复，工作流必须能从持久化的状态原地继续，而不是重跑。

**Q94.【P2】 Critic / Debate 什么时候有效？**
一句话：有效的条件：批评者有**外部信息源或客观判据**（跑测试、查文档、对 checklist）——这时它是真验证；无效的典型：同水平模型"空对空互评"（生成者说好，批评者说可以更好），往往只是把自信的输出磨得更圆滑，成功率提升有限甚至为零，成本翻倍。

展开：关键洞察一句话：**没有新信息进入的 debate ≈ 两个同样偏见的人互相点头。** 两个同水平的模型互评，它们共享同样的知识盲区——A 写错了一个事实，B 的知识里也没有这个事实，它只会评价"写得挺流畅、结构不错"，错误原样通过。研究结论也是这个方向：同模型 debate 在事实性任务上的提升经常不显著，而它让调用次数翻倍，性价比是负的。

什么情况下有效——判断标准是"批评过程有没有新信息进来"：

1. **critic 带工具**：真的去跑测试验证代码、去查原文核对引用是否存在——这是外部事实来源，能抓住生成者知识盲区里的错误；
2. **critic 换视角**：不是"你觉得好不好"，而是分别从安全/性能/正确性三个专用 prompt 各挑一轮刺——不同视角的检查清单是新信息；
3. **reflexion 式**：把上一轮具体的失败反馈（报错信息、测试结果）喂进下一轮——错误信号是真实世界给的，不是模型自己想的。

判别口诀（值得原样记住）："**批评必须能产出可执行的修改依据，否则是表演。**"

陷阱：这题考批判性思维，答出"何时是假提升"比背概念值钱——面试官用这题区分"用过 API"和"算过账"的人。
