# 五、多智能体与编排（参考答案）

---

**Q83. 多 agent 拓扑有哪些？**

一句话：四种主流：① Orchestrator-Worker（一个主管拆解分派、汇总结果）——最通用；② 流水线（A→B→C 串行接力）——阶段清晰的流程（解析→生成→审核）；③ 辩论/评审（生成者 + 批评者互搏）——质量要求高、有客观判据的任务；④ 群聊/swarm（自由移交控制权）——灵活但难控，生产慎用。

展开：选型口诀：能流水线不编排，能编排不群聊——控制流越显式越好治理。orchestrator 的关键设计：任务拆解粒度、结果验收标准（worker 交付怎么判合格）、失败重派策略。加分点：说"拓扑是演化的——先单 agent，测出瓶颈（上下文装不下/单点太慢）再拆"，没人一开始就该上多 agent。

---

**Q84. 什么时候拆多 agent？拆错的代价？**

一句话：拆的真实理由只有三个：① 上下文装不下（每个子任务需要各自的大量专属上下文）；② 需要并行提速（独立子任务 fan-out）；③ 需要不同的"专业配置"（不同模型/不同工具集/不同 system prompt，避免互相干扰）。其他理由（"看起来高级"）都是伪需求。拆错的代价：成本×N、延迟可能反升（协调开销）、错误传播链变长、评测归因困难。

展开：单 agent + 好工具能解决的就别拆——多 agent 的本质是用工程复杂度换上下文隔离和并行度。反面信号：子任务间高频互相依赖、需要共享大量中间状态 → 拆了反而更慢（协调成本 > 并行收益，连 Q92）。这题的正确姿势是给出"拆的前置检查清单"，而不是背模式。

---

**Q85. Sub-agent 上下文隔离？**

一句话：主 agent 给子 agent 一段任务描述 + 必要材料，子 agent 在自己的独立上下文里跑完（查 20 个网页、翻 10 个文件），只把**结论摘要**交回主 agent——过程的海量中间信息不污染主上下文。

展开：为什么重要：主 agent 上下文是稀缺资源，20 个页面的原始内容进去 = 窗口爆炸 + 注意力稀释；隔离后主 agent 只看到"每个子任务 200 字的结论"，能同时掌控全局。类比：管理者不读下属的所有原始邮件，只读报告。代价：信息有损——子 agent 不知道哪些细节对全局关键，所以任务描述里要写清"汇报应包含什么"。这是多 agent 存在的最硬理由（上下文经济学）。

**Q86. DAG 并行执行怎么处理？**

一句话：把计划表示为任务图（节点=子任务，边=依赖），入度为 0 的任务并发跑，完成的任务解锁后继节点；汇总节点等待所有前驱完成。要点：依赖声明要显式、失败传播策略明确（上游挂了下游跳过还是重试）、设全局超时。

展开：实现不必造轮子：图编排框架（LangGraph 的 send/并行分支）或任务队列（Celery/Temporal 思想）都有现成原语。关键坑：① 隐式依赖——子任务 B 实际需要 A 的结果但图里没画边，跑出来才发现，靠评测和 trace 补图；② 汇总的信息压缩——10 个子结果进主上下文前先各自摘要。加分点：DAG 适合"可静态分解"的任务，分解本身动态的场景（查着查着才知道还要查什么）用 orchestrator 动态派发更合适。

**Q87. A2A 和 MCP 的分工？**

一句话：MCP 连接"agent ↔ 工具/资源"（垂直集成：能力供给）；A2A（Agent-to-Agent，Google 发起）连接"agent ↔ agent"（水平协作：不同团队/公司建的 agent 互相委托任务、交换进度）。一个管"我有什么工具"，一个管"我怎么和同行 agent 合作"。

展开：A2A 的核心概念：Agent Card（能力自我描述，供发现）、任务生命周期（委托 → 状态回报 → 交付）。为什么 2026 值得知道：跨组织 agent 协作是企业落地的下一环（你的差旅 agent 调用航司的订票 agent）。诚实的答法：协议层在快速演化、格局未定，重点是理解问题本身（异构 agent 互操作：发现、鉴权、任务语义），而不是死记协议名。

**Q88. 多 agent 框架怎么选？自研边界？**

一句话：优先级：① 先试单 agent；② 流程可预期 → 图编排（LangGraph）；③ 需要高度动态、追求控制力 → 自研 orchestrator loop（几百行：模型 + 工具注册 + 消息传递 + 状态存储）；④ 快速原型 → 轻量 handoff 模式（如 OpenAI Swarm 思想：agent 间移交 + 共享上下文）。自研的合理边界：核心 loop 值得自研（你才真正掌控上下文工程和成本），但别自研向量库、评测平台这类通用件。

展开：选型真实考量：团队对框架的掌控力（出 bug 时能否读源码定位）、迁移成本（框架 lock-in）、可观测性集成。加分观点："框架的价值在前期快，生产系统的复杂度最终都会穿透框架抽象——所以核心 loop 保持薄、可读、可调试。"

**Q89. 状态共享：黑板 vs 消息传递？**

一句话：黑板（blackboard，共享工作区）：所有 agent 读写同一份结构化状态——信息透明、易查全局，但会争写、且人人都看到一切（上下文膨胀 + 信息过载）；消息传递：agent 间点对点发摘要——隔离好、职责清，但信息可能滞留、全局视图难拼。实践主流：**共享状态 + 受控读写 + 各 agent 只订阅相关部分**的混合。

展开：设计核心问题是"谁能看到什么"：全部共享 → 子 agent 上下文被无关信息污染（失去隔离意义）；完全隔离 → 重复劳动和矛盾结论。折中：状态分层（全局任务目标 / 各子任务工作区 / 结论区），orchestrator 负责跨层搬运摘要。这题考的是分布式系统老问题在 agent 场景的新皮，能类比"微服务共享数据库 vs API 通信"的权衡直接加分。

**Q90. 子任务失败怎么传播？**

一句话：失败传播策略按任务关系定：独立子任务 → 失败隔离，继续跑其余，最终报告标注部分失败；下游依赖上游 → 级联取消或用降级结果占位（"该数据暂不可得"）；关键路径失败 → 整体失败并回报卡点。核心：**部分成功必须是可表达的状态**，不能静默当全成功。

展开：工程实现：每个子任务带"重要性"标记（关键/可选），可选任务失败不阻塞交付但要在最终结果里如实声明（"3 项完成，1 项失败：原因是…"）。最危险的失败模式是静默降级——worker 失败、orchestrator 没察觉，产出一个缺数据的报告却标"完成"。防线：验收标准显式化 + 汇总时强制对账（计划 N 项 vs 实际 M 项）。

**Q91. 多 agent 评测难在哪？**

一句话：三个难：① 归因难——端到端失败时不知道是 orchestrator 拆错了、worker 干砸了还是信息传递丢了；② 组合爆炸——agent 配置 × 拓扑 × 任务类型的矩阵跑不完；③ 评测环境更重——要 mock 多个 agent 的行为。解法：组件级评测（单测每个 agent 的职责）+ trace 驱动的失败归因（Q71）+ 小规模端到端回归。

展开：实操：给每个 agent 定独立的输入→输出契约，用单 agent 评测集先各自达标，再拼装跑端到端；失败案例用 trace 回放定位到具体 agent 的具体轮次。加分点：说"多 agent 的失败模式单 agent 没有——通信语义（任务描述歧义）、交接遗漏、重复劳动，这些要专门造评测用例"。

**Q92. 多 agent 的成本延迟放大效应？**

一句话：每个 agent 每步都是一次完整 LLM 调用，N 个 agent × M 步 = N×M 倍调用，协调开销（互相等待、重试、开会式讨论）还会加延迟——并行收益经常被协调成本吃掉。控制：限制 agent 数量和轮数预算、子 agent 用小模型、结论而非过程传递（Q85）、并行只在真正独立的任务上用。

展开：一个数字感：3 个 worker 各跑 10 轮 × 每轮 5k token = 150k token，还没算 orchestrator——多 agent 任务的花费轻松是单 agent 的 5~10 倍。判据："并行的物理收益（IO 等待重叠）是否大于协调的逻辑成本？"拆 10 个 agent 各干 1 分钟的活，可能不如 1 个 agent 串行 5 分钟——加上排队和失败重试的话。答案里带数字是关键。

**Q93. HITL 在多 agent 工作流的插入点？**

一句话：四个经典插入点：① 计划批准后执行前（成本最低的干预点——方向错了这时拦）；② 敏感操作执行前（资金、外发、删除，每个 worker 的敏感工具调用）；③ 阶段交付物验收（worker 的产出经 orchestrator 汇总后人工审再进下一步）；④ 异常升级（失败超限、置信度低）。粒度原则：审批对象是"有风险的决策点"，不是"每个 agent 的每步"。

展开：多 agent 特有问题：多个并行 worker 同时要审批怎么办（审批队列 + 批量确认 UI）；审批超时策略（默认拒绝还是挂起）；审批人看不到子 agent 上下文时怎么给出足够信息做决策（审批卡片要含：做什么、为什么、风险、可选项）。连回 Q65/Q68：每个插入点都需要状态持久化支撑。

**Q94. Critic / Debate 什么时候有效？**

一句话：有效的条件：批评者有**外部信息源或客观判据**（跑测试、查文档、对 checklist）——这时它是真验证；无效的典型：同水平模型"空对空互评"（生成者说好，批评者说可以更好），往往只是把自信的输出磨得更圆滑，成功率提升有限甚至为零，成本翻倍。

展开：关键洞察：没有新信息进入的 debate ≈ 两个同样偏见的人互相点头。有效的模式：critic 带工具（真的去验证引用是否存在、代码是否跑得通）、critic 用不同视角的 prompt（从安全/性能/正确性分别挑刺）、reflexion 式（把上轮失败的具体错误反馈进下轮）。判别口诀："批评必须能产出可执行的修改依据，否则是表演。"这题考批判性思维，答出"何时是假提升"比背概念值钱。
