# 八、工程化与推理部署（参考答案）

---

**Q120.【P0】 流式输出怎么实现？TTFT 为什么重要？**
一句话：后端用 SSE（`Content-Type: text/event-stream`）或 WebSocket 转发模型的逐 token 流，前端增量渲染；TTFT（首 token 时间）是体感核心——总时长相同的情况下，"立刻开始逐字出"和"干等 10 秒一次性出"是两个产品。

展开：把延迟拆成两段理解：

1. **TTFT（首 token 时间）** = 网络传输 + 排队等待 + **prefill**（模型要把你整个输入读完算一遍，输入越长这段越慢）+ 第一个 token 的解码时间。用户点完发送后的"死等感"全来自这里；
2. **吐字速度**（之后每秒出多少 token）——决定剩余体感，用户看到字在动就不焦虑了。

优化 TTFT 的手段按性价比：缩输入（prompt 瘦身、前缀缓存让重复前缀跳过 prefill）、选 prefill 快的服务；最关键的是流式必须**端到端贯通**——模型那边在流式输出，但你自己的网关/框架把整个响应攒齐了再返回给前端 = 白搭，这是最经典的线上事故。工程细节：SSE 经过 Nginx 等反向代理时会被缓冲，要显式关掉（`X-Accel-Buffering: no`），并用心跳保活防止代理掐掉空闲连接。

陷阱：面试官常追问"用户感知延迟由什么决定"——答案是 TTFT + 总输出长度，不是服务端总耗时。

**Q121.【P0】 超时/重试/降级怎么设计？**
一句话：超时分两层（连接超时短、读超时按 token 速率估）；重试只对幂等错误做指数退避 + 抖动，尊重 429 的 Retry-After 头；降级阶梯：主模型 → 备用供应商 → 缓存结果 → 排队稍后处理 → 功能性兜底话术。全局配重试预算防风暴。

展开：细节暴露实战经验：

1. 非幂等操作（已开始生成的）不要盲目重试——流式中断后重发 = 用户看到重复内容，要用请求 ID 去重；
2. 429 是常态不是异常——客户端限流（令牌桶对齐供应商 RPM/TPM 配额）优于被动挨打；
3. 降级不是偷偷的——降级响应要标记（换模型了/结果可能变差），监控降级率。

加分点："熔断：错误率超阈值直接短路到备用，给上游喘息。"

**Q122.【P1】 KV Cache 是什么？显存怎么估？**
一句话：自回归解码每生成一个 token 都要对"所有历史 token"做注意力；KV cache 把每层每头的 K、V 缓存下来避免重算——用显存换时间，解码从 O(n²) 降为每步 O(n)。

展开：先理解为什么需要它。生成第 100 个 token 时，注意力要用它的 Q 去和前 99 个 token 的 K、V 做计算。如果不算缓存，每生成一个新词都要把前 99 个词的 K、V 全部重算一遍——而且前面每多生成一个词，后面每个新词的重算量都变大，总计算量是 O(n²)。但 K、V 只取决于已经确定的输入，根本不会变——那就第一次算完存起来，之后直接查表。这就是 KV cache：**用显存空间换掉重复计算**。

显存估算公式（面试常考）：`2 × 层数 × KV头数 × head_dim × 序列长 × batch × 精度字节`（分子上的 2 = K 和 V 各存一份）。

例：7B 模型（32 层、32 头、head_dim 128）fp16 单条 4k 序列 ≈ 2×32×32×128×4096×2B ≈ 2GB——注意 7B 模型权重 fp16 也才 14GB，一条 4k 序列的缓存就吃掉 2GB，batch 一大缓存总量反超权重。这就是长上下文显存爆炸的原因：缓存大小随序列长度**线性增长且每个请求各存一份**。

衍生考点：GQA/MQA（多个 Q 头共享一组 KV 头，直接把缓存压到几分之一）、MLA（DeepSeek 的思路：不缓存完整 K/V，只缓存一个低秩压缩的 latent 向量，注意力计算时再投影回 K/V——GQA 压的是"头数"，MLA 压的是"每个头存多少内容"，长上下文下缓存能省近一个量级，是当前推理优化的热点）、KV cache 量化（连 Q124，存成 INT8/INT4 再省一半以上）、前缀缓存（相同前缀的 KV 只算一次、后续请求直接复用；**agent 多轮循环是最大受益场景**——system prompt + 工具定义每轮完全不变，每轮只追加新消息，前缀命中率越高成本越低，这是 agent 成本优化的第一杠杆，连 Q129）、以及"为什么批量越大 KV cache 越是瓶颈"——权重全 batch 共享一份，缓存却是每条序列一份。

**Q123.【P1】 PagedAttention 和 continuous batching 解决什么？**
一句话：PagedAttention（vLLM 核心）把 KV cache 像操作系统虚拟内存一样按固定大小 block 分页管理——消除为"未知生成长度"预留连续显存的巨大浪费，显存利用率上去 → batch 能开大 → 吞吐提升 2~4 倍。continuous batching：迭代级调度，每步解码后动态插入/移出请求，不像 static batching 要等整批中最长的跑完——解决"短请求陪跑长请求"的排队浪费。

展开：两个优化共同指向同一瓶颈：KV cache 显存是吞吐的核心约束（连 Q122）。

**PagedAttention**。先看它解决什么：请求到来时你不知道它会生成 50 个 token 还是 500 个。传统做法是按"最坏情况"（比如 max_tokens=2048）一次性预留一整块**连续**显存给这条序列的 KV cache——结果平均只用了零头，剩下的全空占着，别的请求进不来。类比操作系统：早期内存要给程序整块连续空间，碎片严重；虚拟内存把内存切成固定大小的页、按需分配、用页表映射——PagedAttention 对 KV cache 做了一模一样的事：切成固定大小的 block 按需分配，逻辑上连续、物理上散落。浪费从"预留的 60~80%"降到 block 内部的零头。

**Continuous batching**。static batching 是攒一批请求一起进、一起出：一批里混了 10 token 和 1000 token 的请求，短请求完成后它占的位置空转，GPU 干等最长的那个结束才放下一批。continuous batching 把调度粒度从"批"细化到"解码步"：模型每生成一步，就看一眼队列——做完的移出、排队的插进来，GPU 每一步都是满的。类比餐厅：static 是一桌十人必须全员吃完才翻台；continuous 是谁吃完谁走、空位立刻安排新客。

一句总结："vLLM 的胜利是显存管理的胜利。"——被追问"为什么 static batching 差"时用上面陪跑的例子答。

**Q124.【P1】 量化（INT8/INT4）敢不敢用？**
一句话：把权重从 fp16 压到 INT8（几乎无损，常用 W8A8/SmoothQuant）或 INT4（有小损失，GPTQ/AWQ/GGUF 系），换显存减半到 1/4、带宽省 → 吞吐升。敢用：聊天、RAG 问答等容错场景上 INT4 通常可接受；不敢用：精确数值计算、代码生成、以及对"退化 1% 都不行"的场景——且必须过自己的评测集再上。

展开：为什么压位数能提速？解码阶段是**访存受限**的：每生成一个 token 都要把全部权重从显存搬到计算单元，瓶颈不在算得多快，而在搬得多快。权重从 2 字节（fp16）压到 1 字节（INT8）或 0.5 字节（INT4），搬运量同步减半到 1/4——所以小 batch 下吞吐提升明显。量化做的事：把权重数值从连续的浮点映射到低精度的整数网格上（每组配一个缩放系数），精度损失来自"网格不够细"，这就是 per-channel/per-group 量化（分组越细、每组网格越贴合数值分布，损失越小）和 KV cache 量化（长上下文再省一截显存）的意义。

陷阱回答："量化有损所以不用"——错。正确姿势是"量化版 vs 原版跑同一评测集，差距在容忍内就上"，把决定交给数据而不是直觉。聊天场景对个别 token 的措辞差异不敏感，INT4 的质量损失基本被容错吸收；但代码生成对 token 级精度敏感，要实测。

**Q125.【P0】 自部署 vs API？**
一句话：四维决策：① 数据合规（数据不能出域 → 私有化没商量）；② 成本结构（API 按 token 付费零运维，自部署 GPU 是固定成本——量大且负载平稳时自部署摊薄更便宜，量小或波动大时 API 省钱）；③ 定制深度（要改模型行为/微调专属版 → 开源自部署灵活）；④ 运维能力（没有 GPU 工程团队就别硬上）。混合是常态：核心敏感场景私有化，长尾场景走 API。

展开：算账示范（面试加分）：每天 100 万次调用 × 平均 1k token，API 成本约 X 元/天；自部署 4×A100 的固定成本 ÷ 产出 token 数 = 每 token 成本——临界点大概在"持续高利用率"才划算。容易漏的点：模型升级节奏（API 方永远用最新，自部署要自己追版本）和保障（SLA、容量规划）。

**Q126.【P0】 成本优化清单？**
一句话：按杠杆从大到小：① 模型路由（简单请求小模型，Q128）；② 缓存（前缀缓存 Q129 + 相同请求结果缓存）；③ 上下文瘦身（prompt 精简、历史压缩、工具结果裁剪）；④ 输出控制（max_tokens 上限、prompt 要求简洁——输出 token 贵且慢）；⑤ 批处理（离线任务走 batch API 通常半价）；⑥ 微调小模型替代大模型（量特别大时摊得平）。

展开：答题关键是**先测量**：trace 里按"功能 × 模型 × token 类型（输入/输出/缓存命中）"拆成本账，找出大户再下手——经验分布：20% 的功能占 80% 成本。反直觉点：输入 token 便宜但很多（RAG 塞一堆上下文），输出 token 贵但少——两个都要管但优先级看账单。加分点：说"成本优化必须配护栏指标（质量不回退），否则省下的是小钱赔掉的是口碑"。

**Q127.【P0】 高并发的限流/排队/优先级？**
一句话：入口令牌桶限流（按 token 配额不只按 QPS——LLM 的成本和负载都按 token 算）；排队带优先级队列（付费用户 > 免费，在线交互 > 离线批量）；用户体验保底：排队时透明告知预计等待、支持异步通知、超载时降级到小模型而不是直接报错。

展开：LLM 特有：① 一个长请求占 GPU 秒级到分钟级，并发控制要按"在解码中的请求数"和 token 吞吐双重限制；② 公平性——防止单个大客户/单用户占满配额（按租户分桶）；③ 削峰填谷——非实时的任务（文档批量摘要）引导到夜间低峰 batch，这是最便宜的扩容。加分点："限流的终极目标不是拒绝，是把有限的 GPU 花在最高价值的请求上。"

**Q128.【P1】 模型路由/cascade 怎么设计？**
一句话：三档：① 规则路由（按功能/长度/语种，零成本但不智能）；② 小模型分类器路由（预测"这条请求需要多强的模型 + 难度分"）；③ cascade 级联——先小模型跑，置信度低或校验不过再升级大模型，绝大多数请求止步于便宜档。路由信号：任务类型、历史成功率、用户档位。

展开：用一个具体流程理解 cascade：用户问"把这句话翻译成英文"→ 小模型先答 → 校验器检查（格式合法？自评置信度高？）→ 通过，成本 1/10 完成；用户问"分析这段财报的风险点"→ 小模型答完自评置信度低 → 升级大模型重跑。核心权衡在**升级判断的准确性**：误降级（大模型该上的没上）伤质量，误升级（都丢给大模型）费钱。校验器设计分两类：可程序化校验的（JSON 合法、代码跑得过）用规则，确定且免费；不可校验的（开放问答质量）用自评置信度或双模型一致性交叉验证。加分点："cascade 的本质是投机执行——用便宜的试错换取平均成本下降，和 speculative decoding 是同一个思想在不同层面的体现。"（这句跨层连接非常加分）

**Q129.【P1】 Prompt cache 什么时候生效？**
一句话：前缀匹配生效——请求的 prompt 与缓存过的前缀完全一致（逐 token 化后逐个比对）才命中，命中部分按大幅折扣计费且 prefill 加速。组织 prompt 的铁律：**静态内容前置、动态内容后置**——system prompt、工具定义、few-shot 示例放最前，用户消息、检索结果、时间戳等变化内容放最后。

展开：为什么是前缀匹配？prefill 阶段模型按顺序读输入、算 KV cache（连 Q122）——读到第 N 个 token 时，前 N 个 token 的计算结果只由前 N 个 token 决定。所以只要请求的开头部分和之前完全一样，这段的 KV cache 就能直接复用，不用重算；一旦某个 token 不同，从那里往后全部作废。这就解释了"静态前置、动态后置"：公共部分放前面大家共享一份缓存，各自变化的部分放后面各算各的。

经典翻车：把当前时间戳或用户 ID 放在 system prompt 开头 → 每个请求前缀从第 1 个 token 就不同 → 缓存全 miss。第二坑：多轮对话要把历史完整前缀保留（改写历史 = miss），追加式更新对话才吃缓存——每一轮的缓存都是上一轮的延长。第三：不同供应商缓存 TTL 和最小命中长度不同（如 1024 token 起缓存），上线前查文档。加分点：缓存命中率是个监控指标，故意组织 prompt 结构去优化它。

**Q130.【P1】 私有化/信创部署注意什么？**
一句话：三件套：① 许可合规——开源模型许可证各异（Apache 2.0 友好 vs Llama 系列的 7 亿月活限制 vs 部分非商用），商用前逐个核；② 数据不出域——全链路内网闭环（embedding、rerank、LLM 全私有化），注意第三方组件的隐性外呼（telemetry）；③ 审计与安全——调用日志留痕、模型资产访问控制、输出留档可追溯；国内另加生成式 AI 服务备案与内容标识义务（连 Q140）。

展开：硬件维度（信创场景）：国产算力适配（算子支持、推理引擎兼容）常比预期费时，选型时就验证目标模型在目标硬件上的推理栈成熟度。容易被忽略：**更新机制**——私有化后的模型/prompt 升级流程、回滚、与中心评测的联动，别私有化完变成"无人看管的孤儿系统"。

**Q131.【P1】 灰度发布与回滚？**
一句话：三层配置各自灰度、统一回滚：① 模型层（新旧模型按流量比例切，API 的 pinned 版本 / 自部署多副本）；② prompt 层（配置中心管理，热更新，按版本灰度）；③ 编排/agent 配置层（工具集、阈值、路由规则同样版本化）。每层灰度都看同一套护栏指标（质量、成本、延迟），异常自动回滚或告警。

展开：LLM 特有风险：prompt 和模型有交互效应（A prompt 配 B 模型好好的，模型升级后同一 prompt 变差）——所以灰度要按"组合"测，评测矩阵 = prompt 版本 × 模型版本（连 Q24/Q103）。回滚的工程前提：一切可变配置不硬编码、有版本、切换是配置操作而不是发版。一句总结："LLM 系统的发布单元不是代码，是'代码 + prompt + 模型'的三元组。"
