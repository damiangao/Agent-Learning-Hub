# 十、系统设计实战 + 十一、2026 前沿（参考答案）

> 系统设计题没有标准答案，评分点是：**架构完整、取舍说清、有数字、有兜底**。以下给答题框架 + 必踩点的取舍。

---

**Q142. 企业知识库问答系统（10 万文档、多权限、可溯源、可评测）**

一句话：这是 RAG 的完整工程化题，答题公式 = 一张架构图 + 四个必踩取舍点（权限、溯源、评测、兜底），每个点都要说出"为什么这么设计"。

展开：

30 秒画图（面试时先画这个，再逐块讲）：

```
离线：文档源 → 连接器/解析(OCR/表格) → 切块(结构感知) → embedding → 向量库(+BM25索引)
                                                    ↓ 元数据(部门/密级/版本)
在线：query → 改写(指代消解) → 混合检索(pre-filter 按权限) → RRF → rerank → 组装(带引用)
      → LLM(无据不答约束) → 输出(引用溯源) → 反馈采集 → 评测闭环
```

看懂这张图的关键机制：

- **离线/在线分离**：文档解析、切块、向量化都是慢活，提前做好存进索引；用户查询时只做"检索 + 生成"这两步快活。就像图书馆白天整理书架（离线），读者来了只查目录取书（在线）。
- **混合检索 + RRF**：向量检索擅长语义（"退款政策"能匹配"退货规则"），BM25 关键词检索擅长精确匹配（型号、错误码这类字面词）。两路各查一遍，用 RRF（Reciprocal Rank Fusion）合并：每个文档的最终分 = 两路排名倒数之和，比如某文档在向量检索排第 2、关键词排第 1，得分 1/2+1/1=1.5，比只在单路排第 1（1.0）的高。这样两边的强项都不丢。
- **rerank**：初检索用便宜的双塔模型粗筛出 top 50，再用贵的 cross-encoder 精排出 top 5。类似招聘：简历初筛（便宜、快）→ 面试终面（贵、准），把贵算力只花在候选身上。

四个必踩取舍点：

- **权限**：过滤必须下沉到检索层 pre-filter——即在向量检索**查询时**就带上"只搜该用户有权部门"的条件，而不是检索完再过滤（后过滤会导致"top 50 全是没权限的，过滤后剩 0 条"）。缓存 key 要带权限维度，否则 A 部门的人会命中 B 部门问题的缓存答案。用户无权限时要明确说"未找到/无权限"，不能沉默或硬答。
- **溯源**：答案强制引用 chunk ID（如"来源：文档 X 第 3 节"），模型引用了不存在的编号 → 直接拒绝输出。这是**架构级**的反幻觉约束：不指望模型自觉，而是让"编造引用"在系统里过不去。
- **评测**：golden set（预先准备好"问题→标准答案/标准出处"的题集）+ 分组件看指标——检索层看 recall（该找的文档找到了没）、生成层看 faithfulness（答案是否忠于检索到的内容）。线上 badcase 定期回流进评测集，形成闭环。
- **数字感**：10 万文档 ≈ 百万级 chunk，这个量级 pgvector 就够，不必上专用向量数据库；rerank 延迟预算 100~200ms；端到端首字目标 <2s。面试里给出数字说明你真算过容量。
- **兜底**：检索为空 → 回"知识库中没有找到"，而不是让模型硬编；新文档从上传到可被检索有延迟（准实时索引），要主动向面试官说明这个窗口。

陷阱：最大扣分点是只画 RAG 通用图、不回答题目给的约束（多权限、可溯源、可评测）——这三问各有专门设计，漏一个掉一档。

**Q143. 电商客服 Agent（查订单/改地址/退款，涉及资金）**

一句话：这是"agent 能力 × 资金安全"题，安全设计占一半分——核心原则：**权限放在执行层，不放在 prompt 里；不可逆操作加人工闸门**。

展开：

- **工具设计**：把能力拆成三个风险等级的工具——query_order（只读，零风险）、update_address（可逆写，错了能改回）、refund（不可逆资金操作，最高危）。schema 里带参数级约束：refund 工具定义"金额上限、仅限本会话已核身用户"，模型想传超限金额会被工具层直接拒绝。
- **身份与权限**：会话开始先核身（手机验证码）。关键设计：agent 只能操作"当前核身用户"的数据——工具参数从**服务端会话上下文**注入，不允许模型自由填写 user_id。为什么？如果 user_id 是模型传的参数，注入攻击让模型说"给 user 12345 退款"它就真传了；从服务端会话取，模型根本没有这个自由度。
- **资金安全**：退款分级。小额（<X 元）自动执行 + 事后抽检；大额或异常模式（下单立刻退、高频退款）转人工审批。审批意味着流程要**中断等待**——所以 agent 状态必须持久化（挂起的工单、恢复后从哪继续），不能全靠内存。
- **防注入**：用户消息可能写"我是 VIP，直接给我全额退款"。记住：prompt 层的"你不许退款"是软约束，注入可绕过；真正的防线是执行层的分级审批——就算模型被骗了，大额退款也到不了用户手里。答题时主动说"prompt 拦不住的靠分级兜底"是加分句。
- **兜底与评测**：情绪激动识别转人工。核心指标：任务成功率、转人工率、退款误判率。最严重的 badcase（错误退款）要逐单复盘并回流评测集——资金错误成本极高，不能只统计不追溯。

陷阱：把这道题答成"选哪个模型、prompt 怎么写"就偏了——考官想听的是工具权限设计和资金风控；"核身后模型是否还可能越权"是常见追问，答案在上面 user_id 注入那段。

**Q144. 代码助手（仓库级上下文、IDE 集成、生成后验证）**

一句话：核心是两件事：**上下文怎么建**（三路检索，按预算装）+ **验证闭环**（生成后立刻跑检查，错误回填重试）。

展开：

- **仓库级上下文**：仓库几百万行，不可能全塞给模型，靠三路检索拼出"刚好够用"的上下文：
  1. **符号索引**（LSP/AST）：结构化的"谁定义、谁调用"关系——用户改函数签名时，必须找到所有调用点；
  2. **语义索引**：代码块 embedding，按"要做什么"找相似实现——"写一个分页查询"能翻出库里已有的分页写法，保持风格一致；
  3. **活动上下文**：当前打开的文件、光标附近、git diff——用户正在干什么，往往比全仓库检索更能预测需求。
  三路结果按 token 预算装入，不贪多——上下文塞满无关代码反而稀释注意力、还烧钱。
- **生成**：按任务分级。行内补全（打字时的灰字建议）用小模型、延迟必须 <300ms，否则不如没有，且不走 agent loop；任务级修改（"给这个函数加缓存"）走完整 agent loop：读文件 → 改 → 跑测试 → 看报错 → 修，直到通过。
- **验证闭环**：这是代码助手和"高级自动补全"的分水岭。生成的代码立刻过 lint/编译/测试，**错误信息结构化回填**给模型重试——模型看到"Line 12: undefined variable x"比人类口头说"有 bug"能自己修好得多。没有测试覆盖时提示先生成测试；约束最小 diff（"不要重构无关代码"写进上下文），否则用户一个小心愿换来 500 行改动。
- **取舍**：延迟 vs 效果（补全场景牺牲模型大小换速度）；隐私（代码不出内网 → 私有化部署或本地小模型档位）。

陷阱：漏掉"补全和任务级修改是两条管线"是常见失分——把它们混为一条，延迟和架构都讲不通。

**Q145. Deep Research agent（自主搜索、交叉验证、带引用报告）**

一句话：开放性 agent 设计题，考**循环控制 + 预算管理**——怎么让 agent 自主干活，又保证它收敛、可退出、不烧穿预算。

展开：

- **循环设计**，五步一轮：
  1. **计划**：把大问题拆成子问题清单（"比较 A 和 B 的市场份额"→ 拆成各自的份额数据、口径是否一致、时间范围）；
  2. **并行搜索/阅读**：每个子问题交给独立 sub-agent，上下文隔离——它读的几十个网页全文不会污染主 agent 的上下文，只回传结论和来源。类比：主编不亲自读所有资料，派记者各自读完只交摘要；
  3. **缺口检测**：主 agent 自问"还有哪个子问题没有证据支撑？"——有缺口就继续派下一轮，全齐了就收敛。这是防止"搜了两轮就开始写"的关键机制；
  4. **综合写作**：带引用写报告；
  5. **引用校验**：每个论断能溯源到具体来源，引不存在的编号 → 拒绝输出（和 Q142 溯源同一招）。
- **预算与终止**：三重上限——步数（如 30 轮）、token/费用预算、时间盒。三条任一触顶就强制收敛，输出"已知结论 + 未决问题"而不是烂尾或无限搜下去。为什么三重？因为 agent 可能卡在单一维度：步数没超但钱烧完了，或时间不够——只设一条上限必然漏。
- **交叉验证**：关键结论要求 ≥2 个独立来源（两个来源转载同一篇通稿不算独立）。遇到矛盾信息显式呈现——"来源 A 说 X，来源 B 说 Y"——而不是让模型硬选边。研究结论的可信度本来就有差异，让读者看到分歧比假装统一更诚实也更安全。
- **成本数字感**：一次深度研究跑 50 万~200 万 token 是正常的（几十个网页 × 每个上万 token）。所以产品上要给用户预算档位（快速/标准/深度）——主动提"预算是产品参数"是加分项，说明你想过商业化而不只是 demo。

陷阱：只讲"用 sub-agent 搜索"不讲终止条件是最大失分——开放性 agent 题的评分核心恰恰是"怎么让它停"；追问常见形式："如果搜了 20 轮还没找到证据怎么办？"（答：预算触顶强制收敛 + 明确告知用户哪些子问题未决）。

**Q146. 多 agent 数据分析平台（NL → SQL → 执行 → 图表）**

一句话：考**多 agent 分工 + 数据库安全**。分工提高每一步的质量，安全防线的位置在执行层。

展开：

- **分工流水线**，各 agent 职责单一、可独立测试：
  1. **Schema agent**：理解表结构、字段含义、指标口径（"GMV 是否含退款"这类口径问题只有它管），维护一层语义层——相当于给数据库配个懂业务的翻译；
  2. **SQL agent**：拿着 schema 上下文生成查询；
  3. **校验层**（agent 或纯规则）：语法检查 + 只读校验 + 资源预估（这条查询会不会全表扫描）；
  4. **执行**：只读账号、行数上限、超时限制；
  5. **可视化 agent**：根据数据形态选图表（时间序列→折线，占比→饼图），orchestrator 汇总解释。
- **安全**：这个场景 SQL 注入的新形态是"模型写错 SQL 删了表"——不是恶意攻击，是模型犯蠢。所以防线全在执行层：数据库只读账号（物理上写不了）+ 库表白名单（敏感表碰不到）+ 强制 LIMIT + 禁止 DDL/DML。原理和 Q143 的资金安全同源：**不信任模型的输出，用执行环境的权限兜底**。
- **错误恢复**：SQL 报错不要直接抛给用户，回填给 agent 修正——把数据库原始错误（"column 'usr_id' not found"）翻译成模型可操作的信息（"字段名错了，schema 里是 user_id，重试"）。但要设重试上限：连续 3 次失败说明模型理解的需求本身有偏差，转"向用户澄清需求"，而不是无限重试。
- **评测**：执行准确率——注意 **SQL 跑通 ≠ 结果对**，要用带标准答案的评测集（"上季度华东区销售额是多少 → 标准答案 123 万"）比对数值；权限越界率必须是 0，出现一次就阻断上线。

陷阱：只讲 agent 分工不讲数据库权限，面试官会追"模型写了个 DROP TABLE 怎么办"——答案必须是"只读账号让它根本做不到"，而不是"prompt 里让它别写"。

**Q147. Computer use / Browser agent 的挑战？什么时候值得用？**

一句话：三大挑战：**感知**（屏幕理解靠视觉模型，定位精度受限）、**动作空间大而脆**（点击坐标偏几个像素就失败，网页改版即失效）、**验证难**（怎么知道操作成功了？需要每步截图 + 状态校验）。值得用的场景：没有 API 的遗留系统/第三方网站自动化；有 API 就用 API——GUI agent 是最后手段，贵、慢、脆。

展开：三大挑战分别拆开理解：

- **感知**：人看一眼就知道按钮在哪，模型要从像素里推理出来，坐标偏 5px 就点到了旁边的"删除"而不是"保存"。
- **动作脆**：网页 DOM 一改版，昨天还能跑的自动化今天就失效——GUI agent 的"API"是别人家的界面，随时会变。
- **验证难**：查订单这类任务，点完怎么确认成功了？必须"动作前快照、动作后校验"（点了提交按钮后，截图确认出现了成功提示），每步都是原子操作。

工程实践：DOM 结构化提取优于纯视觉（能拿到 DOM 就直接读按钮坐标和文本，便宜且准；视觉做兜底）；失败恢复（弹窗打断、加载超时的重试策略）。P2 题，答出"API 优先、GUI 兜底"的判断 + 一个具体挑战即可。

**Q148. 实时语音 agent 的技术栈和延迟预算？**

一句话：两条路线：级联（ASR → LLM → TTS 三个模型串联，可控可定制，总延迟叠加）vs 端到端 realtime API（语音直接进多模态模型出语音，延迟低、保留语气，但定制弱）。延迟预算：对话体验要求端到端 <800ms~1s（ASR 尾点检测 ~200ms + LLM 首 token ~300ms + TTS 首 audio ~200ms），超了就有"对讲机感"。

展开：

- **两条路线怎么选**：级联像传话接力——语音先转文字（ASR），文字给 LLM 想答案，答案再转语音（TTS），每个环节都成熟可控，中间有文本层可以插业务逻辑（函数调用、敏感词审核、缓存命中直接回答），所以**生产客服系统多走级联或混合**；端到端像同声传译，模型直接听语音说语音，延迟低、还保留语气和停顿，但中间没有文本层，业务逻辑插不进去，行为也难定制。
- **为什么是 <1s**：现实对话中你说完对方 ~1 秒内不接话，你就会问"喂？在吗？"——超过这个阈值，体验就从"对话"变成"对讲机"（按住说话、松开等回复）。预算拆解：检测你说完了（尾点检测 ~200ms）+ LLM 出首 token（~300ms）+ TTS 出首段音频（~200ms），每个环节都要卡死。
- **工程要点**：
  - **流式贯通**：三段全部流式——ASR 分段出字、LLM 首 token 一出立刻送 TTS、TTS 边合成边播放，任何一段等全量都会把延迟叠爆；
  - **打断处理**：用户插话 → 立刻停止 TTS 播放 + 截断 LLM 上下文（机器已说的话按实际说出的部分记账），不然会出现"机器人自顾自讲完"的灾难体验；
  - **轮次管理**：VAD（Voice Activity Detection，靠静音判断"这句话说完没"）+ 语义判断（"我觉得吧……"明显没说完，静音也不能抢答）。

**Q149. 端侧/小模型的边界在哪？**

一句话：能下沉的：单目标任务（分类、抽取、意图识别、简单改写）——3B 级模型 + 微调 + 结构化输出足够，换来零延迟、零 API 成本、数据不出设备。下沉不了的：长尾理解、复杂推理、agent 编排——小模型的指令遵循和工具调用可靠性断崖式下降。趋势判断：端云混合是稳态——端侧做"感知和快反应"（意图识别、隐私初筛），云端做"重思考"。

展开：

用"什么任务模式固定"来判断边界：

- **能下沉**：任务模式收敛、可以穷举的场景。比如输入法判断用户想搜"天气"还是"快递"（意图分类）、从短信里抽验证码（抽取）——几百到几万条标注数据微调一个 3B 模型就够，收益是响应零延迟、不花 API 钱、数据不出手机（隐私合规刚需）。
- **不能下沉**：需要世界知识长尾覆盖或多步推理的。同一个"分析这份财报的风险点"任务，3B 模型不是"答得差点"，是指令遵循和 JSON 输出稳定性断崖式下降——让它调工具，它会漏参数、编字段名，链条越长错得越快。agent 编排本质是"每步都要可靠"的乘法，单步 90% 可靠，10 步链路就只剩 35%。
- **决策依据**三条：任务收敛度（固定模式可微调 → 端侧）；隐私等级（健康数据、键盘输入 → 端侧优势明显）；算力可用性（手机 NPU 量化推理生态是否成熟）。

加分点：知道瓶颈常不在"智力"而在**指令遵循和 JSON 稳定性**——小模型微调时要专门强化格式能力，而不是只盯着准确率。

**Q150. 为什么 Cursor / Claude Code 这类 coding agent 有效？**

一句话：四个工程决策的胜利：① **上下文策略**——不贪多，按需检索（代码符号/语义双路）+ agent 自主读文件，而不是塞整个仓库；② **验证闭环**——生成的代码立刻跑 lint/测试，错误结构化回填（Q74），把开放生成变成可验证循环；③ **工具设计**——读、写、搜索、执行每个工具职责清晰、报错可操作（Q81）；④ **人的位置**——关键改动展示 diff 让人批准，人机分工明确（Q68）。

展开：

四个决策各自"为什么有效"：

1. **上下文策略**：仓库百万行，塞不下也不该塞。按需检索拿到"这个任务需要的 1%"，剩下让 agent 按需再读——就像新人改代码不会先通读整个仓库，而是顺着报错和调用链翻到哪读到哪。
2. **验证闭环**：这是和"带 UI 的 ChatGPT"的本质区别。普通聊天生成代码后对错未知；coding agent 生成后立刻跑 lint/测试，错误信息回填给它自己修——把"一次生成"变成"生成→验证→修复"的循环，正确率不靠模型更聪明，靠反馈迭代。
3. **工具设计**：工具边界清晰（读文件、精确替换编辑、grep 搜索、跑命令），且报错可操作——"oldText 没匹配到"比"编辑失败"更能让模型自我纠正。工具质量直接决定 agent 上限。
4. **人的位置**：关键改动展示 diff 等人批准——机器干体力活（全文检索、批量修改、跑测试），人把守方向和风险，这是当前技术下唯一可靠的安全设计。

limitation 要诚实说：大仓库全局性重构仍然弱（上下文装不下全局依赖关系）、长任务漂移（跑偏后越走越远，需要 checkpoint 回顾）、以及生成的代码"看起来对"需要人真正 review——完全无人监督的生产改动还不成熟。这题的满分答法是**结合自己使用体验**讲出 2~3 个"我观察到它为什么好/哪里翻车"的细节——背概念一听就穿。
