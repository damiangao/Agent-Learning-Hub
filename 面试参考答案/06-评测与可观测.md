# 六、评测与可观测（参考答案）

---

**Q95. 离线评测 vs 在线评测？**

一句话：离线（评测集上跑分）管"变更前把关"——快、可回归、可对比，但分布可能失真；在线（真实用户流量）管"实际效果"——A/B 指标、用户反馈、badcase 回流，但慢、贵、有风险。上线前靠离线，上线后靠在线，badcase 反哺离线集，闭环。

展开：分工：离线回答"这个版本比上个版本好吗"（回归），在线回答"用户真的满意吗"（效果）。只做离线的坑：评测集过时、刷分（过拟合评测集）；只做在线的坑：把用户当测试小白鼠，事故直接发生在线上。加分点：给出各自典型指标——离线：准确率/格式合规率/faithfulness；在线：任务完成率、点踩率、人工转接率、留存。

---

**Q96. LLM-as-a-Judge 的偏差？**

一句话：用强模型按 rubric 给输出打分，替代人工。已知系统性偏差：位置偏好（对比评测偏爱第一个/某个位置的答案）、长度偏好（偏爱长答案）、自我偏好（偏爱和自己风格/自己生成的答案）、以及 rubric 外漂移（评分不稳定）。

展开：为什么还是主流：人工标注贵且慢，judge 便宜且可无限重复。用对的前提：① rubric 具体可判（"答案是否包含正确订单号"而不是"答案好不好"）；② 对比评测时**交换位置跑两次**消除位置偏差；③ 用和被评模型不同家的模型当 judge 减少自我偏好；④ 定期抽样人工校准（Q97）。一句加分话："judge 是仪器，仪器要校准，不校准的 judge 产出的是带系统误差的假数据。"

---

**Q97. 怎么校准 judge？**

一句话：抽 100~200 条做人工标注金标准 → 算 judge 与人的一致率（如准确率/Cohen's Kappa）→ 低于阈值（如 Kappa < 0.6）就改 rubric / 加 few-shot 评分示例 / 换 judge 模型 → 迭代到可信后再大规模使用；上线后定期重校（模型或 rubric 变更时）。

展开：实操细节：分歧样本是金矿——逐条看 judge 和人为什么分歧，通常是 rubric 有歧义（"相关性"没定义清楚）；把仲裁结论写成 few-shot 例子喂给 judge，一致率通常显著上升。另外分指标校准：judge 判"格式对错"可能 95% 一致，判"有用性"可能只有 70%——对低一致性的维度降权或改用人工。

---

**Q98. Golden set 怎么建、怎么维护？**

一句话：建：从真实流量 + 历史坏例 + 边界构造中攒 200~1000 条，每条带标注答案/判分标准，版本化管理；维护：固定评审节奏（如每月）、新 badcase 持续入库、定期淘汰不再代表业务的旧样本；分歧：双人背靠背标注，不一致的仲裁并回写标注规范。

展开：关键心法：golden set 是"尺子"，尺子本身要稳——样本变更要记录 changelog（这次改了 50 条，指标波动多少归因于尺子 vs 归因于代码）。防过拟合：核心集（不大动，做回归）+ 漂浮集（定期换新，防刷分）。加分点：说"标注规范和代码一样要 code review，标注分歧率是规范质量的指标"。

---

**Q99. 模型指标好但业务指标不动？**

一句话：三种典型原因：① 评测集和真实分布脱节（刷分了）；② 优化的是代理指标不是用户价值（格式合规率涨了，但用户要的是答得对）；③ 业务侧瓶颈不在模型质量（入口流量、交互设计、响应速度）。定位：拉齐分布（评测集换新样本）→ 按用户分群看在线指标 → 找"离线涨了在线没涨"的具体 case 对比分析。

展开：这是 open-ended 题，考排查思路。经典案例：RAG 准确率从 85% → 92%，客服点踩率没变——分析发现点踩的用户全是问"什么时候发货"这种要调订单 API 的，知识库答得再好也没用：瓶颈在能力覆盖不在质量。教训：指标要和"用户任务能否完成"挂钩（任务完成率 > 文本相似度）。能讲一个自己版本的这类故事，非常加分。

**Q100. LLM 功能的 A/B 怎么做？**

一句话：和传统 A/B 相同的骨架（随机分流、足够样本量、统计显著性），不同在三处：① 噪声大——同一输入输出都随机，指标要按会话/用户聚合而非按请求；② ② 指标模糊——主观满意度要靠代理（完成率、点踩率、重试率、人工转接率）；③ 护栏指标必设——新版本效果涨了但成本/延迟/P0 事故率不能涨。

展开：样本量意识：点踩率从 5% 降到 4%（相对提升 20%）在基率低时需要巨大流量才能显著——所以小流量产品常用"离线评测 + 小流量人工评估"过渡，别硬等 A/B 显著。加分点：分层看效果（新用户 vs 老用户、简单 vs 复杂 query），新版本经常是"复杂 case 变好、简单 case 变差"，整体均值掩盖一切。

**Q101. 评测怎么接进 CI/CD？**

一句话：把评测集跑分做成 CI 的一个 stage：prompt/模型/检索参数的 PR 触发自动评测 → 关键指标低于基线或显著回退则 block 合并 → 评测报告（分数 + 与上版 diff + 坏例样例）贴在 PR 评论里。

展开：和单测的差别要讲清：① 慢且贵（LLM 调用）——全量集只在合并前跑，PR 早期用快照子集；② 概率性——设置容忍带（分数波动 ±1% 内放行）而不是零容忍，防 CI 红绿抖动；③ 基线管理——main 分支的最近分数是基线，模型升级时要重定基线。这是"把 LLM 工程当软件工程做"的最直接体现，2026 面试高频。

**Q102. 幻觉自动检测方法？**

一句话：三类：① 引用溯源——生成的每个论断必须能对应到检索片段，对不上就是幻觉（最实用）；② faithfulness judge——让另一个模型逐句判断"该句是否被给定上下文支持"（RAG 三角：query、context、answer 两两评）；③ 自一致性/置信度——多次采样答案矛盾、或 token 级 logprob 异常低，标记可疑。

展开：工程首选"无据不答 + 引用强制"：架构上要求答案带引用编号，程序校验引用真实存在且确实支持该句（支持性可用 NLI 模型或小 LLM 判），校不过的答案降级为"根据资料未能找到"。加分点：说清检测的位置——生成后拦截（保住底线）+ 评测集里持续监控幻觉率（看趋势），两手都要有。

**Q103. 上游模型升级导致漂移怎么办？**

一句话：发现：固定"哨兵评测集"每天定时跑，分数异常告警（供应商可能已静默换模型）；输出指纹监控（输出长度分布、格式合规率突变也是信号）。应对：prompt/参数重跑评测集定位回退点 → 定向修 prompt → 重大回退则切版本锁定的旧模型（API 的 snapshot 版本或自托管）→ 给供应商提工单。

展开：预防优于发现：生产系统**锁版本**（用带日期的模型版本号而不是 "latest"），升级当成一次变更走完整评测流程。这题的深层考点：你是否把"模型"当成会突变的依赖来管理（和"依赖升级引发 bug"同构）。答出"哨兵集 + 版本锁定"两个词就到位。

**Q104. Tracing 工具记录什么？**

一句话：一次调用的完整谱系：trace（一次任务）→ span 层级（检索 span、LLM span、工具 span），每个 LLM span 记：模型/版本、完整输入消息、输出、token 用量、延迟、成本、错误；检索 span 记：改写后的 query、召回列表与分数；工具 span 记：调用参数、结果摘要、耗时。

展开：工具选型顺口：LangSmith（配 LangChain 生态顺）、LangFuse（开源可自托管，国内合规友好）、或 OpenTelemetry 自建（大厂统一观测栈）。价值不在记录在**用法**：按坏例过滤 trace、对比两次执行的输入差异、统计各环节延迟/成本分布。加分点："trace 的终极消费者是评测——每条线上 badcase 一键转成评测用例。"

**Q105. 人工标注的质检和一致性？**

一句话：规范先行（可操作的正反例文档）→ 双人背靠背标 → 不一致率监控 + 分歧仲裁（第三人/讨论）→ 一致性量化（Cohen's Kappa）→ 分歧案例回流修订规范 → 标注员定期校准测试。

展开：为什么 Kappa 而不是简单一致率：要剔除"碰巧一致"的成分，Kappa < 0.4 说明规范有问题，先修规范别急着用数据。实操坑：标注规范的模糊词（"相关"“高质量"）必须换成可判定的判据（"包含答案所需的具体数字/步骤"）；标注员对业务熟不熟直接影响质量——给上下文文档。加分点：说"LLM 预标注 + 人工复核"能提效 2~3 倍，但要抽检 LLM 标注质量防止系统性带偏。

**Q106. 组件级评测为什么必要？**

一句话：端到端只给一个总分，坏了不知道坏在哪——把 RAG 拆成检索（recall/MRR）和生成（faithfulness/答案正确率）分别评，才能定位"检索没召回"还是"召回了对但没答好"，优化才有靶子。端到端的盲区：组件误差互相抵消或互相放大，总分看不出。

展开：典型场景：端到端准确率 70% 不动，一拆发现检索 recall@5 已经 95% 但生成正确率只有 73%——瓶颈在生成侧，改 prompt/模型而不是继续调检索。反过来也成立。扩展到 agent：工具调用准确率、规划质量、终止合理性都是可拆的组件指标。这题和 Q41（排障二分法）是同一种思维的评价面，一起答。

**Q107. 用户反馈闭环怎么设计？**

一句话：采集（显式：点赞点踩、修正；隐式：重试、改写再问、中途放弃、转人工）→ 归因（badcase 自动分类：检索没中/答错/格式问题/超范围）→ 入库（badcase 进评测集 + 优先级队列）→ 修复 → 带着修复版本回归验证 → （可选）通知用户"你反馈的问题已改进"。

展开：隐式信号常比显式更有信息量：用户重问一次 = 变相点踩。工程关键：反馈必须带完整上下文快照（当时的 trace），否则事后无法复现归因。优先级：高频 × 严重的坏例先修——反馈闭环也是需求排序的依据。加分点：给闭环一个指标——"badcase 复发率"（修复后同类问题是否再出现），衡量闭环是否真转起来了。

---

**Q108. 评测集太大跑不起，怎么 sampling？**

一句话：分层抽样保分布（按类目/难度/语言分层，每层按比例抽）；核心集 + 随机浮动集（核心防回归、浮动防过拟合）；变更感知采样——改动只影响某类功能时优先跑相关子集；定期全量（如每周）兜底。

展开：先算清楚再优化：单条成本 × 全量 = 每次回归花费，如果全量只要几块钱，别优化，直接全量（ponytail 精神：先测量，再投机）。真正的成本大头通常是端到端 agent 评测（每个 case 跑几十轮工具调用）——这时优化的是 case 的代表性而不是跑得快。

---

**Q109. 公开 benchmark 为什么不能说明你的应用好？**

一句话：三个错位：分布错位（MMLU 考学科知识，你的场景是客服工单）、任务错位（它考模型能力，你考"模型+RAG+prompt+工具"的系统效果）、判分错位（它有标准答案，你的"好"是业务定义的）。模型榜是选型的初筛信号，系统好不好只能用自己的评测集回答。

展开：正确的使用姿势：公开榜做**粗筛**（缩候选名单）+ 泄露风险意识（榜单题可能进了训练数据，分数虚高）+ 真正决策依据自己建的 golden set（Q98）。一句总结加分："你的评测集就是你的 benchmark——它是唯一和你的分布一致的。"
