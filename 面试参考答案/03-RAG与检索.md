# 三、RAG 与检索（参考答案）

---

**Q31.【P0】 完整 RAG 链路？**
一句话：**离线**：文档 → 解析 → 切块 → 向量化 → 入库（含元数据）；**在线**：query → 改写 → 召回 top-k → 重排 → 组装上下文 → LLM 生成（带引用）。

展开：先把两条链路分开记，面试时画出来就赢了大多数人。

1. **离线（建索引）**：解决"机器怎么提前消化知识"——文档解析成纯文本（PDF 里的表格是重灾区）→ 按语义边界切成块 → 每块用 embedding 模型变成向量 → 存进向量库，每块附带元数据（来源、标题、时间、权限）。
2. **在线（查 + 答）**：解决"来了问题怎么用这套索引"——用户问题先改写（补指代、纠错）→ embedding 后去库里召回 top-k 相似块 → reranker 精排出最相关的几条 → 拼成带编号的上下文 → LLM 按上下文回答并标注引用。

为什么面试爱考：每个环节的输出是下一环节的输入，**质量逐级衰减**——解析丢表格 → 后面全错，且错误在下游看起来像"模型不行"。所以排查问题永远从链路头走到尾（Q52）。加分点：说出"在线链路每一环都要可单独评测"（Q106），这是生产思维。

**Q32.【P0】 RAG vs 微调怎么选？**
一句话：RAG 解决"模型不知道"（注入知识，可随时更新、可溯源），微调解决"模型表现不像"（改行为、风格、格式）；决策顺序：prompt → few-shot → RAG → 微调，微调是最后手段。

展开：两者治不同的病，用表格记：

| | RAG | 微调 |
|---|---|---|
| 治什么 | 模型**不知道**（缺知识） | 模型**表现不像**（风格/格式/行为） |
| 知识更新 | 换文档即生效 | 数据过期要重训 |
| 溯源 | 能给出处 | 给不了 |

判断标准三问：① 缺的是事实知识还是能力？知识 → RAG（把资料塞进上下文，模型本来就会读资料）；② 知识多久变一次？天天变 → RAG（微调的数据永远过期）；③ 需要溯源吗？合规场景必须 RAG（能给出处）。微调真正合适的场景：稳定领域的输出风格/格式/术语、小模型顶替大模型省成本、RAG 也救不了的领域语言（如高度专业的行话）。二者可叠加：微调管行为 + RAG 管知识。

陷阱：一上来就"微调吧"是最常见错误答案——先反问"确定是知识问题，而不是 prompt 问题？"

**Q33.【P0】 chunk_size 和 overlap 怎么定？**
一句话：没有万能值，起点 256~512 token + 10~20% overlap，然后用检索评测（recall@k）扫参数；核心原则是**按语义边界切**（段落、标题、条款），而不是数 token 硬切。

展开：先懂"为什么要切块"，再记参数。向量检索的基本单位是"块"——一个块被 embedding 压成一个向量，所以**一个块只能有一个主题**，这个向量才能代表它。

两个方向都会翻车：

- **切太大**（如一整页）：一个块混了三个主题，向量变成"平均画像"，跟哪个 query 都像又都不像 → 检索不精；且进上下文的无关内容多，噪声引发幻觉。
- **切太小**（如一两句）：语义不完整，embedding 看不出这段在讲什么；答案需要的上下文被切碎，检索到了也答不全。

overlap 是什么：相邻块重叠 10~20% 内容，缓解"关键句正好被切在边界上"的问题；代价是内容存两份、可能重复召回。它是补丁，不是解法。

调优流程：固定 100+ 条评测 query → 扫 chunk_size × top_k 网格 → 看 recall 和端到端答案质量，不要拍脑袋。加分点：结构感知切分（按 markdown 标题/条款号切，让块边界 = 语义边界），以及父子块（Q49）——检索用小块、生成给大块——是比调 overlap 更有效的解法。

**Q34.【P0】 Embedding 模型怎么选型？**
一句话：四看：任务榜单表现（MTEB/C-MTEB）、语言匹配、部署约束（维度、尺寸、能否私有化）、实际数据上的评测结果——最终用自己的数据说话。

展开：流程：① 初筛：看 MTEB 检索子榜，中文场景看 C-MTEB（bge、gte、Qwen-Embedding 系）；② 约束过滤：私有化 → 开源；API 生态 → OpenAI/Cohere embedding；③ **拿自己 200~500 条真实 query-文档对跑评测**，公开榜单和你的领域分布可能完全不同；④ 权衡维度：维度大效果略好但存储/计算贵（如 3072 vs 768，差距常比想象小）。陷阱：换 embedding 模型 = 全库重建索引（所有向量要重新算），选型时要想到迁移成本。

**Q35.【P0】 向量库怎么选？**
一句话：按规模和运维能力：原型/百万级 → pgvector（Postgres 顺手就用了）或 FAISS（纯内存、单机）；千万~亿级、高并发、需分布式 → Milvus/Qdrant；已有 ES 且要混合检索 → ES dense vector。

展开：决策维度：① 数据量（FAISS 单机内存上限、pgvector 亿级吃力）；② 过滤需求（元数据过滤性能，pgvector 借力 SQL 索引很强）；③ 运维成本（多一个中间件 = 多一份高可用/备份/监控负担）；④ 混合检索支持（ES 天然 BM25+向量）。加分点：反主流但正确的答案——"大部分业务 1000 万条以下，pgvector 就够了，别为了简历引入 Milvus"。先满足需求，再谈扩展。

**Q36.【P1】 HNSW vs IVF-PQ？**
一句话：HNSW 是多层跳表式近似图，召回率高、查询快，但内存大（存全部向量和图边）；IVF-PQ 先聚类分桶再量化压缩，内存小几个量级，但召回率损失明显。内存够用选 HNSW，内存紧张/超大规模选 IVF-PQ。

展开：先懂背景：几百万条向量逐条算相似度太慢，所以向量库都用**近似最近邻（ANN）**索引——牺牲少量精度换百倍速度。两个流派：

1. **HNSW（图索引）**：类比"社交网络找熟人"。建索引时让每个向量记录几个近邻（像好友关系），并组织成多层：顶层稀疏（长途跳）、底层稠密（精细找）。查询时从顶层快速跳到目标区域，逐层向下逼近最近邻。参数 `ef` 是搜索宽度旋钮：调大 → 多看候选 → 召回高但变慢。优点：召回率高、查询快；缺点：向量和图边全部驻内存，内存开销大。
2. **IVF-PQ（压缩索引）**：两级省内存。IVF 先把向量空间聚成 nlist 个簇，查询只搜最近的 nprobe 个簇（跳过大部分数据）；PQ 再把每条向量切成子段、每段量化成 1 字节编码——一条 1536 维浮点向量（约 6KB）压成几十字节。内存省几个量级，代价是量化损失精度，召回明显下降。

一句话选型：内存够用选 HNSW（效果好、简单），内存紧张/亿级规模选 IVF-PQ（或 HNSW + 量化组合）。陷阱：关键词是"**近似**"——两者都不是精确检索，召回率是可调的权衡项不是固定值；说不出 ef / nprobe 各自控制什么，等于没用过。

**Q37.【P0】 为什么混合检索？RRF 是什么？**
一句话：向量检索抓语义但弱于精确匹配（产品型号、人名、错误码常翻车），BM25 抓关键词但不懂同义改写；两者召回互补，用 RRF（倒数排名融合）合并：每条结果的得分 = Σ 1/(k + rank_i)，k 常取 60。

展开：先记两条腿各自的软肋：

- **向量检索**抓语义（"咋报销差旅"能命中"差旅费报销流程"），但弱于精确匹配——搜"ERR_CONN_RESET"可能返回一堆《网络错误概述》，错误码这种字面信息在语义空间里不突出。
- **BM25**（关键词检索）抓字面，搜错误码、型号、人名又准又快，但不懂同义改写——换个说法就搜不到。

生产里两类 query 都存在，所以双路召回、合并结果。合并为什么不能直接比分数？余弦相似度范围 [-1,1]，BM25 分数范围不固定，数值不可比。**RRF 的聪明处：只用排名、不用分数**。每条文档的融合分 = 它在各路结果里的 1/(k + rank) 之和。例子：文档 A 在向量路第 1、BM25 路第 3 → 得 1/(60+1) + 1/(60+3) ≈ 0.032；文档 B 两路都是第 1 → 得 2/61 ≈ 0.033 胜出。"两路都认可"的文档排前面。

加分点：权重版 RRF（可调 dense/sparse 配比，如错误码多的场景加大 BM25 权重）；以及"上 rerank 后融合策略的影响被弱化，但仍决定 rerank 的候选池——融合做差了，正确文档可能根本进不了候选"。

**Q38.【P0】 Reranker 是什么？什么时候值得？**
一句话：bi-encoder（embedding）把 query 和文档各自独立编码，快但粗；cross-encoder（reranker）把 query+文档拼一起过模型逐对打分，准但慢。所以标准链路是"embedding 粗召回 50~100 条 → reranker 精排取 top 5~10"。值得的场景：召回质量是瓶颈、延迟预算允许（百毫秒级）；不值得：candidate 池本来就小、或延迟极敏感的 C 端首屏。

展开：分两步理解为什么两者都存在：

1. **bi-encoder**：query 和文档**各自独立**编码成向量再比相似度。关键优势：文档向量可以**离线提前算好**存进库里，查询时只算一次 query 向量 → 毫秒级扫百万文档。代价：每篇文档被压成一个向量，细节必然丢失，query 里的词和文档里的词从没有直接交互过 → 粗。
2. **cross-encoder**：把"query + 某篇文档"**拼在一起**过模型，两边的词直接做注意力交互，能捕捉细粒度匹配（代词指代、条款对不上号都看得出来）→ 准。代价：每篇候选都要跑一次前向计算 → 慢，且**无法离线建索引**（拼接结果随 query 变化）。

单个不够用，就上漏斗：embedding 快速粗召回 50~100 条（宁多勿漏）→ reranker 只对这几十条精细打分 → 取 top 5~10 进上下文。这是速度换精度的经典权衡。

陷阱：说清两者**不能互换位置**——cross-encoder 无法建索引，只能在线对少量候选打分；bi-encoder 精度不够时直接喂生成则噪声大。

**Q39.【P0】 top_k 怎么定？**
一句话：两段式：召回 top 20~100（宁多勿漏，交给 rerank），进上下文只放 3~10 条（rerank 后的相关阈值过滤）；依据是评测——看 recall@k 曲线的拐点和你上下文的噪声容忍度。

展开：召回段的 k 由"漏掉代价"决定：法务/医疗场景漏检代价高 → k 大；闲聊场景 → k 小。生成段的条数由"上下文质量"决定：塞 50 条中等相关的进去，lost in the middle + 噪声幻觉会让答案变差——**更多上下文常常更糟**，这是反直觉但正确的点。加分点：按相关性分数动态截断（如只保留 rerank 分数 > 0.3 的条数）比固定条数更稳。

**Q40.【P0】 检索质量怎么量化？**
一句话：有标注用 recall@k（前 k 条里有没有正确文档）、MRR（正确结果排名的倒数的均值）、NDCG（考虑分级相关性和位置折损）；没标注就用 LLM 生成伪 query 建评测集，或用"答案可溯源率"等代理指标。

展开：三个指标各答一个问题：

- **recall@k**："该找到的找没找到？"例：正确文档在前 5 条里出现过，recall@5 就算命中。答"找没找到"，不管排第几。
- **MRR**："找到的排得靠不靠前？"正确文档排第 2 位贡献 1/2，排第 10 位贡献 1/10——排名越靠前分越高。rerank 优化的就是它。
- **NDCG**：再进一步——相关性分等级（完美相关 > 部分相关），且排得越靠后打折越狠。

冷启动套路：让 LLM 从每篇文档生成 3~5 个"用户可能会问的问题"，构成 query-doc 对——虽不完美，但足以横向对比方案。加分点：强调组件级评测（检索、生成分开测）是 RAG 调优的前提——端到端准确率不告诉你该改哪一环。

**Q41.【P0】 怎么区分检索失败和生成失败？**
一句话：看证据链：检索到的片段里**有没有**能支持答案的信息——有但答错 = 生成失败（改 prompt/换模型）；没有 = 检索失败（改召回/改写/切块）；检索到了但**没被引用**也可能是中间环节丢了（rerank 砍掉/上下文超长截断）。

展开：这个二分法是 RAG 排障的核心框架。细分四种情况：① 检索对+生成对（理想）；② 检索对+生成错 → 生成侧问题：prompt 指令不清、上下文太乱、模型能力不足；③ 检索错+生成"对"——最危险：模型用参数知识编了看似合理的答案（幻觉），要靠"无据不答"约束；④ 检索错+生成错 → 全链路问题。修法方向完全不同，先分类再动手。

**Q42.【P1】 查询改写有哪些手段？**
一句话：multi-query（LLM 把问题改写成多个变体，多路召回取并集，治"表述偏移"）、HyDE（让模型先生成一个假设答案，用答案的 embedding 去检索，治"问句和文档句式不匹配"）、step-back（先抽象出上位问题再检索，治"细节问题缺上下文"）。

展开：这些手段都在治同一个病——**用户的问法和文档的写法存在分布差异**。用户问"咋报销差旅"，文档写"差旅费报销流程及标准"，原句直接检索可能命中不了。三种药：

1. **multi-query**：LLM 把问题改写成 3~5 个变体（口语版/术语版/中英文版），多路召回取并集去重。用多样性覆盖差异，治"一种表述搜不到"。
2. **HyDE**：让 LLM 先盲写一个假设答案，再用**这个答案的 embedding** 去检索。犀利在：文档本来就是"答案的样子"，答案和答案的相似度天然高于问句和答案的相似度。代价：多一次生成，且假设答案错了会带偏检索。
3. **step-back**：先抽象出上位问题再检索。例：问"《Redis 设计与实现》195 页讲了什么" → 先退化为"该书主要内容"，拿到全书概览再答细节。治"细节问题缺背景"。

成本提醒：改写 = 多一次 LLM 调用（延迟 + 费用），简单场景先用规则/同义词典兜底，评测证明检索是瓶颈再上 LLM 改写。

**Q43.【P1】 复杂文档怎么解析？**
一句话：分层武器库：纯文本类直接抽；PDF 版式复杂用版面分析模型（layout 检测 + 表格识别）；扫描件 OCR；表格转 markdown/HTML 保留结构；代码按语法树切分。关键：**解析质量决定 RAG 上限**，值得花重投入。

展开：常见坑：① PDF 双栏排版导致阅读顺序错乱；② 表格被拍平成乱码字符串，语义全毁——表格要么整表入索引（生成"表格描述+摘要"辅助检索）要么结构化入库；③ 页眉页脚水印污染文本；④ PPT/图表类"图像型知识"需要多模态模型生成文字描述再入库。加分点：说"入库前人工抽检解析结果"是性价比最高的质量手段。

**Q44.【P1】 pre-filter vs post-filter？**
一句话：pre-filter 先按元数据（部门、时间、类型）缩小候选集再做向量检索；post-filter 先向量检索再过滤。"过滤后结果为空"通常出在 post-filter：top-k 里恰好没有满足条件的。

展开：用一个例子记住两者的坑。库里有 100 万条文档，其中 5000 条属于"华东区"，query 带过滤条件 `region=华东`：

- **post-filter**（先检索后过滤）：向量检索按相似度取 top 50，这 50 条里可能只有 2 条是华东区的，过滤完只剩 2 条——明明库里还有 4998 条华东区文档，它们只是相似度没挤进全局 top 50。
- **pre-filter**（先过滤后检索）：先在 5000 条华东区文档里做向量检索 → 结果一定满足条件。但坑在另一头：过滤太严时候选集只剩几十条，HNSW 这类图索引在极小候选集上近邻搜索质量下降，甚至被迫暴力扫描。

工程折中：过度采样（检索 3k 条再过滤取 k），或选对过滤友好的索引结构。这道题考的是你是否真调过库。

---

**Q45.【P1】 文档更新怎么同步？**
一句话：以文档为同步单位建立"源 → 块"的映射：文档更新时重切块、重嵌入、按 doc_id 删旧插新（原子替换）；删除文档必须级联删所有块；高频更新场景用版本号/更新时间戳做增量。

展开：经典事故：源文档删了，向量库里的块还在 → RAG 引用已废弃信息。要点：① 块的 metadata 必须带 doc_id/chunk_id/版本，这是级联删除的钥匙；② 更新期间避免"新旧并存"造成检索到两版本（先写新、校验、再删旧，或用别名切换）；③ 全量重建 vs 增量：小库全量重建简单可靠，大库必须增量 + 定期对账（源和索引的 doc 数比对）。

**Q46.【P1】 多轮对话的检索怎么做？**
一句话：先做 query 改写（指代消解 + 省略补全）再检索：把"它呢？"结合历史改写成完整独立问题，可以开小模型 + 短 prompt 干这事，成本可控。

展开：例子：轮 1 问"公司年假几天"，轮 2 问"病假呢"——直接拿"病假呢"去 embedding 检索必挂（这四个字在向量空间里几乎没有信息量）。必须先改写成"公司病假有几天"才能命中。改写这一步只依赖对话历史，不需要查库，所以用小模型就够。注意三点：① 改写用的历史别太长（最近 2~3 轮足够），控制成本；② 用户明确切换话题时要识别出来，别错误合并历史；③ 多轮检索结果可以和上一轮结果做融合（用户可能在追问同一个话题）。

**Q47.【P1】 GraphRAG 是什么？值不值得上？**
一句话：在向量索引之上建实体关系图（实体为节点、关系为边），检索时能做多跳推理和全局性问题（"A 和 C 有什么联系""这个领域的主要主题有哪些"）；代价是构建和维护成本高数倍。值得：实体关系密集、需要多跳/全局摘要的场景（情报分析、医疗、法律文书网）；不值得：普通文档问答——向量 RAG 够用，GraphRAG 是用大炮打蚊子。

展开：先看向量检索为什么搞不定多跳。query"A 公司实控人是谁的亲戚"需要 A → 实控人 → 亲属两次跳转：embedding 相似度一次只能度量"这段话和 query 像不像"，而没有任何一段文档同时包含这三个点，所以单次检索找不到完整答案。GraphRAG 的解法：离线用 LLM 从文档里抽取实体和关系（"A 公司—实控人—张三""张三—亲属—李四"）建图（这步很贵）；检索时图遍历（顺藤摸瓜）+ 向量召回混合。全局性问题（"这个领域的主要主题"）也靠图上的社区摘要回答，向量检索只会返回一堆零散段落。

2026 视角：它是"agentic RAG"的一种实现——用 agent 多步检索替代/补充一次相似度搜索。

**Q48.【P1】 多部门权限怎么做？**
一句话：权限过滤必须下沉到检索层：块的 metadata 带权限标识（部门/密级/用户组），检索时作为强制 filter（pre-filter），且在生成侧再做一层引用校验——绝不能只靠应用层检索完再"挑掉"没权限的。

展开：两个致命错误：① post-filter 或应用层过滤导致"过滤后剩 0 条但回答仍生成"——模型会用参数知识脑补（危险）；② 缓存按 query 存不按权限存 → A 部门命中 B 部门的缓存答案（泄露事故）。要点：filter 和 query 绑定进缓存 key；无权限检索为空时明确回答"没有权限/未找到"而不是硬答。这题其实是安全题，面试官在看你有没有权限意识。

**Q49.【P1】 small-to-big / 父子块检索？**
一句话：用小块（一两句话，语义聚焦）做检索匹配，命中后返回它所属的大块（整段/整节）给 LLM 生成——检索要"准"，生成要"全"，两全其美。

展开：为什么有效：回到 Q33 的矛盾——检索希望块小（一个块一个主题，向量不稀释，匹配准），生成希望块大（单句不够 LLM 作答）。父子块把两件事拆开：检索匹配在子块上做，命中后沿"子块 → 父块"的映射（存 metadata 里，实现就是个 id 指针）把父块交给 LLM。变体：句子级检索 → 返回整段；或"命中块 + 前后各一个邻块"（sentence-window）。成本：多一层映射关系的存储，实现不复杂，是性价比很高的优化，面试答出这题说明有实战。

**Q50.【P0】 RAG 的 golden set 怎么建？**
一句话：100~300 条起步，每条 = query + 标注的正确来源文档/片段 + 标准答案要点；必须覆盖失败模式：精确术语、口语化问法、多跳问题、应拒答问题（库中没有）、多语言；随线上坏例持续回流扩充。

展开：覆盖失败模式比堆数量重要——尤其"应拒答"类（问库里没有的东西，期望回答"未找到"），不测这个你的 RAG 永远在"自信地编"。评分三层：检索层（命中正确文档？）、生成层（答案对？）、溯源层（引用了正确来源？）。加分点：说 golden set 也要版本化，模型/链路升级时同一把尺子量到底。

**Q51.【P1】 中文 RAG 特有问题？**
一句话：分词影响 BM25（中文需分词器，且新词/品牌名切错全盘皆输）、embedding 选中文优化过的模型（C-MTEB 验证）、繁简转换、专名/型号的精确匹配靠混合检索兜底、语义压缩表达（中文更省字但歧义更多）。

展开：实操要点：① BM25 必须配中文分词（jieba 等），行业黑话要加自定义词典；② 繁简混排文档先统一化再入库，否则同一词两套向量；③ 中文数字歧义（"三季度"vs"第三季度"）和缩写（"发改委"）靠查询扩展缓解；④ 中文 embedding 模型别用英文榜单挑。这题考"你真做过中文场景"。

**Q52.【P0】 "答非所问"排查清单？**
一句话：从链路头查到尾：① query 本身（歧义？多轮指代没改写？）→ ② 召回（打印 top-k，正确文档在不在？）→ ③ rerank（在候选里但被砍了？）→ ④ 上下文组装（进了窗口但排在中间被忽略？）→ ⑤ 生成（片段里有答案但模型没答对/没按约束答）→ ⑥ 是不是知识库根本没有（应拒答场景）。

展开：这是 Q41 的实操版。加分答法是"先建可复现的观测"：把每次调用的 query、各阶段结果、最终 prompt 全文都 trace 下来（Q104），否则排查只能靠猜。再给一个结论模板："70% 的'模型不行'最后定位是检索没召回对"——说明你踩过坑。

**Q53.【P1】 Agentic RAG vs pipeline RAG？**
一句话：pipeline RAG 是一次固定流程（改写→检索→生成）；agentic RAG 让模型自主决定**要不要检索、检索什么、检索几轮、要不要换关键词再来**，适合多跳问题、模糊问题、需要交叉验证的复杂任务；代价是延迟和成本成倍涨。简单 FAQ 问答坚决用 pipeline。

展开：判断信号：如果你的评测集里多跳/组合类问题占比高、或单轮检索 recall 卡在瓶颈，值得 agent 化。实现上往往是"检索器作为工具"交给 agent loop。加分点：说混合架构——先跑一次 pipeline，检测到"低置信/引用不足"时才升级为 agentic 多轮检索（级联思想，和 Q128 路由同构）。

**Q54.【P1】 多知识库怎么路由？**
一句话：三层方案：① 元数据路由——库少且边界清晰时用 LLM/分类器先选库再检索；② 联合检索——所有库一起检索，用来源权重区分；③ agent 化——多库作为工具让模型自己决定查哪个、查不到换一个。兜底：路由不确定时联合检索，宁多勿漏。

展开：路由错误的代价是"答非所问"，所以兜底比路由本身重要：低置信时降级为跨库检索 + rerank 统一排序。路由器实现：库的数量少（<10）用 LLM 结构化输出选库（带"其他/多个"选项）；库多时先分类体系或按用户入口分流（产品 FAQ 入口只搜产品库）。加分点：路由也要进评测集——路由错误率是独立指标。
