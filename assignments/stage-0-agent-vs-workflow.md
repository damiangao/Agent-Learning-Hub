## 2. 四个概念区分

### 2.1 Chatbot 是什么？

Chatbot 是一种以对话为主要交互方式的 LLM 应用。用户提出问题或指令，chatbot 根据当前输入和对话上下文生成回答。它通常是被动响应用户，而不是主动拆解长期任务、调用多个工具并持续推进目标。它的核心能力是对话理解和文本生成。

例子：

```text
human：今天上海天气怎么样？
ai：38 度，非常热。
human：有什么建议？
ai：多喝水，吹空调，少出门。
```

---

### 2.2 Workflow 是什么？

Workflow 是预先设计好的步骤序列。每一步做什么、下一步去哪，通常由开发者提前规定。它可以包含 LLM，也可以不包含 LLM。它适合流程稳定、判断条件清楚、输出格式明确的任务。

例子：

```text
用户上传一篇文章 -> LLM 总结文章 -> LLM 提取关键词 -> 保存到数据库 -> 返回摘要和标签
```

---

### 2.3 Agent 是什么？

Agent 是一种目标驱动的 LLM 应用。它不是只回答一次问题，也不是按固定步骤执行，而是会观察当前环境和任务状态，思考下一步应该做什么，选择并调用工具，观察工具结果，再决定是否继续行动。它的关键特征是动态决策和多步闭环执行，同时需要停止条件、权限边界和错误处理。

例子：

```text
Claude Code：用户提出代码任务后，它可以读取文件、分析代码、编辑文件、运行命令、观察结果，并根据结果决定下一步。
```

---

### 2.4 Multi-agent 是什么？

Multi-agent 是多个 agent 按照明确职责和协作协议共同完成任务。它通常适合任务复杂、需要并行处理、需要不同角色互相检查，或者单个 agent 上下文和能力不足的场景。Multi-agent 的重点不是“多个模型聊天”，而是职责拆分、任务分配、结果汇总、冲突处理和停止条件。

例子：

```text
汇总 100 篇文章时，由 manager agent 先制定任务并按主题分类，再分配给多个 worker agent 分别处理不同类别，最后由 reviewer / synthesizer agent 汇总、去重和检查引用。
```

## 3. Agent 基本循环

```text
observe -> think -> act -> observe
```

### 3.1 Observe 是什么？

Observe 是观察现有环境和上下文，包括任务需求、已有状态、上一步工具输出、错误信息、文件内容、网页内容或用户反馈。

### 3.2 Think 是什么？

Think 是根据观察到的信息判断当前状态，决定下一步要做什么：是否需要调用工具、调用哪个工具、用什么参数、是否需要停止、是否需要向用户确认。

### 3.3 Act 是什么？

Act 是执行动作，例如调用工具、搜索资料、读取文件、写文件、运行测试、请求用户确认或输出最终答案。

### 3.4 为什么要再次 Observe？

一轮动作通常不足以完成开放式任务。Agent 需要观察动作结果，判断是否达成目标、是否出现错误、是否需要重试、是否需要换策略，或者是否应该停止。

### 3.5 用一个具体例子说明完整循环

例子场景：

```text
帮我生成一个 hello.txt 文件。
```

循环过程：

```text
1. observe：观察到用户想生成 hello.txt 文件。
2. think：判断可以使用 write_file 工具创建文件。
3. act：调用 write_file 工具写入文件内容。
4. observe：观察工具结果，确认文件已经生成或发现写入失败。
5. 下一步：如果成功，反馈用户已完成；如果失败，根据错误信息重试或请求用户确认。
```

## 4. 什么时候不该用 Agent？

### 场景 1：确定性的计算任务

```text
例如计算金额、汇率、税费、指标公式。
```

为什么不该用 agent：

```text
计算任务有明确规则和正确答案，agent 可能因为模型幻觉或格式问题出错，成本也更高。
```

更适合的方案：

```text
普通脚本、计算函数、规则引擎或数据库查询。
```

---

### 场景 2：编码格式检查

```text
例如 Python 代码格式化、import 排序、静态 lint。
```

为什么不该用 agent：

```text
格式检查有明确规则，agent 不能保证找出所有问题，也不适合替代确定性的静态分析工具。
```

更适合的方案：

```text
ruff、black、eslint、prettier、mypy 等确定性工具。
```

---

### 场景 3：流程稳定的 RAG 问答系统

```text
例如企业内部知识库问答：用户提问 -> 检索知识库 -> 基于引用回答。
```

为什么不该用 agent：

```text
如果任务路径稳定，固定的检索和回答流程更可靠。Agent 可能跳过检索、使用不可靠来源，或者在不需要探索时增加不确定性。
```

更适合的方案：

```text
意图理解节点 -> 检索节点 -> rerank 节点 -> grounded answer 节点 -> citation check 节点。
```

## 5. 我的候选 Agent 场景

### 5.1 我选择的 Agent 场景是

```text
资料研究助手
```

---

### 5.2 这个任务的输入是什么？

```text
输入一个研究主题，以及一些参考资料链接。例如：“Claude Code 的工具调用机制”“Agent harness 如何做权限控制”“MCP 和 Skill 的区别”。
```

---

### 5.3 期望输出是什么？

```text
一份带引用的结构化研究报告，包括主题概览、关键结论、来源链接、不同观点对比、限制和下一步实践建议。
```

---

### 5.4 为什么普通 Chatbot 不够？

```text
普通 chatbot 主要是被动回答用户问题。它可以分析文本，但通常不会主动规划完整研究流程，也不会持续跟踪已经搜索过哪些资料、哪些来源可靠、哪些观点需要交叉验证、是否还缺少反方观点。资料研究助手需要多轮搜索、筛选、比较、引用整理和自我检查，因此普通 chatbot 不够。
```

---

### 5.5 为什么固定 Workflow 不够？

```text
资料研究的中间路径不可预期。搜索结果质量不稳定，关键词可能需要调整，某些资料可能过时或互相矛盾，有时还需要补充搜索反方观点、官方文档或代码仓库。固定 workflow 可以提供骨架，但很难覆盖所有分支；agent 更适合根据中间发现动态调整研究路径。
```

---

### 5.6 这个 Agent 需要哪些工具？

| 工具 | 用途 | 为什么需要 |
| --- | --- | --- |
| web_search | 搜索相关资料 | 找到官方文档、论文、GitHub 仓库、工程博客和反例资料。 |
| web_fetch / read_url | 读取网页原文内容 | 避免只根据搜索摘要判断，降低误读和引用幻觉。 |
| write_file | 保存研究报告 | 形成可复盘、可修改、可提交的学习产出。 |

---

### 5.7 这个 Agent 需要哪些状态或记忆？

```text
当前研究问题、任务进度、已经搜索过的关键词、已经阅读过的资料、来源可靠性判断、待验证的问题、用户偏好的输出格式、历史失败记录。
```

---

### 5.8 这个 Agent 可能失败在哪里？

| 失败模式 | 可能原因 | 如何降低风险 |
| --- | --- | --- |
| 搜索质量低 | 搜索关键词太宽泛，来源不可靠 | 使用多组关键词搜索；优先官方文档、论文、GitHub 和工程博客；记录来源等级。 |
| 信息过时 | Agent 使用了旧文章或者旧 API 文档 | 要求输出发布日期；优先近 1 年资料；涉及 API 行为时查官方文档。 |
| 引用幻觉 | 模型编造来源或误读网页 | 引用必须来自实际抓取的内容；每条关键结论附 URL；最终做 citation check。 |
| 研究范围漂移 | 搜索过程中偏离主题 | 维护研究问题列表；每轮搜索后检查是否服务于原问题。 |
| 总结偏向单一观点 | 只看到了同类资料 | 至少覆盖官方文档、开源项目、技术博客、反例/限制四类来源。 |

## 6. Agent vs Workflow 判断

> 我的场景为什么需要 agent，而不是普通 workflow？

```text
1. 我需要的是灵活的研究能力，而不是固定步骤下的稳定输出。
2. 资料研究的中间步骤不可预期，搜索结果、来源质量和后续问题都会随着发现变化。
3. 我希望系统能探索不同路径，但这种探索必须在明确权限、成本上限、停止条件和可观测日志内进行。
4. 我希望 agent 能在研究过程中与用户交互，必要时请求澄清或修正研究方向。
5. 我希望输出不只是我已经预设好的结果，而是能通过多轮搜索和交叉验证发现我没有想到的资料、限制和实践方向。
6. 固定 workflow 可以提供基础骨架，例如搜索、阅读、总结、引用检查，但 agent loop 更适合处理开放式研究任务中的动态决策。
```

## 7. 我的最小可行版本

### 7.1 第一版只支持什么输入？

```text
文本输入：一个研究主题，以及可选的参考资料链接。
```

### 7.2 第一版只输出什么？

```text
文本输出：一份 Markdown 格式的短研究报告，包含结论、引用链接和下一步建议。
```

### 7.3 第一版只接哪些工具？

```text
web_search：搜索相关资料。
web_fetch / read_url：读取网页原文内容。
write_file：保存研究报告。
```

### 7.4 第一版不做什么？

```text
第一版不运行 bash 脚本，不执行代码验证，不做浏览器自动点击，不做长期记忆，不做多 agent，不自动发布报告。
```
