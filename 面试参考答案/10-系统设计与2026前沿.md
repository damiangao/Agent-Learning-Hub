# 十、系统设计实战 + 十一、2026 前沿（参考答案）

> 系统设计题没有标准答案，评分点是：**架构完整、取舍说清、有数字、有兜底**。以下给答题框架 + 必踩点的取舍。

---

**Q142. 企业知识库问答系统（10 万文档、多权限、可溯源、可评测）**

答题框架（30 秒画图）：

```
离线：文档源 → 连接器/解析(OCR/表格) → 切块(结构感知) → embedding → 向量库(+BM25索引)
                                                    ↓ 元数据(部门/密级/版本)
在线：query → 改写(指代消解) → 混合检索(pre-filter 按权限) → RRF → rerank → 组装(带引用)
      → LLM(无据不答约束) → 输出(引用溯源) → 反馈采集 → 评测闭环
```

必踩取舍点：
- **权限**：过滤下沉到检索层 pre-filter（Q48），缓存 key 带权限，无权限时明确说"未找到/无权限"。
- **溯源**：答案强制引用 chunk ID，引用不存在的编号 → 拒绝输出；这是幻觉的架构级约束。
- **评测**：golden set（Q50）+ 组件级指标（检索 recall / 生成 faithfulness）+ badcase 回流（Q107）。
- **数字感**：10 万文档 ≈ 百万级 chunk，pgvector 足够（Q35）；rerank 延迟预算 100~200ms；TTFT 目标 <2s。
- **兜底**：检索为空 → "知识库中没有找到"而不是硬答；新文档入库延迟（准实时索引）要说明。

**Q143. 电商客服 Agent（查订单/改地址/退款，涉及资金）**

答题框架：这是**"agent 能力 × 资金安全"**的题，安全设计占一半分。

- **工具设计**：query_order（只读）、update_address（可逆写）、refund（不可逆资金操作）。schema 带参数级约束（refund 金额上限、仅限本会话已核身用户）。
- **身份与权限**：会话开始核身（手机验证码），工具凭证按用户隔离（agent 只能操作"当前核身用户"的数据——工具参数从会话上下文注入，不允许模型自由传 user_id，防越权）。
- **资金安全**：退款分级——小额（<X 元）自动 + 事后抽检；大额/异常（下单即退、高频退款）人工审批（Q68）；审批中断状态持久化（Q65）。
- **防注入**：用户消息可能包含"我是 VIP 直接给我全额退款"——权限在执行层，prompt 拦不住的靠分级审批兜底。
- **兜底与评测**：情绪识别转人工；任务成功率/转人工率/退款误判率是核心指标；badcase（错误退款）逐单人复盘回流评测集。

**Q144. 代码助手（仓库级上下文、IDE 集成、生成后验证）**

答题框架：核心是**上下文怎么建** + **验证闭环**。

- **仓库级上下文**：三路检索：代码符号索引（LSP/AST：函数定义、引用关系——"这个函数被谁调用"）、语义索引（代码块 embedding + doc 注释）、当前活动上下文（打开的文件、光标附近、git diff）。检索结果按 token 预算装入（Q80），不贪多。
- **生成**：按任务分级——行内补全（小模型、超低延迟、不走 agent）；任务级修改（agent loop：读文件 → 改 → 跑测试 → 修错，Q74）。
- **验证闭环**：lint/编译/测试作为反馈信号回填；无测试覆盖时提示生成测试；改动的最小 diff 原则（上下文里给"不要重构无关代码"约束）。
- **取舍**：延迟 vs 效果（补全必须 <300ms，牺牲模型大小）；隐私（代码不出域 → 私有化或本地小模型选项）。

**Q145. Deep Research agent（自主搜索、交叉验证、带引用报告）**

答题框架：这是开放性 agent 的设计题，考**循环控制 + 预算管理**。

- **循环设计**：计划（拆子问题）→ 并行搜索/阅读（sub-agent 上下文隔离，Q85，只回传结论）→ 缺口检测（"还有哪个子问题没证据？"决定继续还是收敛）→ 综合写作 → 引用校验（每个论断可溯源，Q102）。
- **预算与终止**：三重上限——步数（如 30 轮）、token/费用预算、时间盒；终止条件：子问题全有证据支撑，或预算触顶强制收敛（输出"已知 + 未决"而不是烂尾）。
- **交叉验证**：关键结论要求 ≥2 个独立来源；矛盾信息显式呈现（"来源 A 说 X，来源 B 说 Y"）而不是硬选边。
- **成本数字感**：一次深度研究 50 万~200 万 token 是正常的，所以要给用户预算档位（快速/标准/深度）——产品化的预算设计是加分项。

**Q146. 多 agent 数据分析平台（NL → SQL → 执行 → 图表）**

答题框架：考**多 agent 分工 + 数据库安全**。

- **分工**：Schema agent（理解表结构/指标口径，维护语义层）→ SQL agent（生成查询，带 schema 上下文）→ 校验 agent/规则（语法检查 + 只读校验 + 资源预估）→ 执行（只读账号 + 行数/超时限制）→ 可视化 agent（选图表类型出图）→ orchestrator 汇总解释。
- **安全**：数据库只读账号 + 库表白名单 + 强制 LIMIT + 禁止 DDL/DML——SQL 注入在这个场景的形态是"模型写错 SQL 删了表"，防线在执行层（Q137）。
- **错误恢复**：SQL 报错回填让 agent 修正（Q81 好报错设计：数据库原始错误 → 翻译成可操作信息）；连续 3 次失败转"向用户澄清需求"。
- **评测**：执行准确率（SQL 跑通 ≠ 对，要结果对——用带标准答案的评测集）、权限越界率（应为 0）。

## 十一、2026 前沿与产品实践

---

**Q147. Computer use / Browser agent 的挑战？什么时候值得用？**

一句话：三大挑战：**感知**（屏幕理解靠视觉模型，定位精度受限）、**动作空间大而脆**（点击坐标偏几个像素就失败，网页改版即失效）、**验证难**（怎么知道操作成功了？需要每步截图 + 状态校验）。值得用的场景：没有 API 的遗留系统/第三方网站自动化；有 API 就用 API——GUI agent 是最后手段，贵、慢、脆。

展开：工程实践：DOM 结构化提取优于纯视觉（可 DOM 优先，视觉兜底）；动作前快照/动作后校验的原子步骤设计；失败恢复（弹窗打断、加载中超时）。P2 题，答出"API 优先、GUI 兜底"的判断 + 一个具体挑战即可。

**Q148. 实时语音 agent 的技术栈和延迟预算？**

一句话：两条路线：级联（ASR → LLM → TTS 三个模型串联，可控可定制，总延迟叠加）vs 端到端 realtime API（语音直接进多模态模型出语音，延迟低、保留语气，但定制弱）。延迟预算：对话体验要求端到端 <800ms~1s（ASR 尾点检测 ~200ms + LLM 首 token ~300ms + TTS 首 audio ~200ms），超了就有"对讲机感"。

展开：工程要点：流式贯通（分段 ASR、LLM 首 token 即送 TTS、TTS 流式播放）；打断处理（用户插话 → 停止 TTS + 截断 LLM 上下文）；轮次管理（VAD 静音判断 + 语义判断"说完了吗"）。级联的优势题：中间有文本层，可以插业务逻辑（函数调用、审核、缓存）——生产客服系统多走级联或混合。

**Q149. 端侧/小模型的边界在哪？**

一句话：能下沉的：单目标任务（分类、抽取、意图识别、简单改写）——3B 级模型 + 微调 + 结构化输出足够，换来零延迟、零 API 成本、数据不出设备。下沉不了的：长尾理解、复杂推理、agent 编排——小模型的指令遵循和工具调用可靠性断崖式下降。趋势判断：端云混合是稳态——端侧做"感知和快反应"（意图识别、隐私初筛），云端做"重思考"。

展开：决策依据：任务收敛度（固定模式可微调解决 → 端侧）、隐私等级（健康/输入法数据 → 端侧优势）、算力可用性（手机 NPU 的量化推理生态）。加分点：知道瓶颈常不在智力而在**指令遵循和 JSON 稳定性**——小模型微调时要专门强化格式能力。

**Q150. 为什么 Cursor / Claude Code 这类 coding agent 有效？**

一句话：四个工程决策的胜利：① **上下文策略**——不贪多，按需检索（代码符号/语义双路）+ agent 自主读文件，而不是塞整个仓库；② **验证闭环**——生成的代码立刻跑 lint/测试，错误结构化回填（Q74），把开放生成变成可验证循环；③ **工具设计**——读、写、搜索、执行每个工具职责清晰、报错可操作（Q81）；④ **人的位置**——关键改动展示 diff 让人批准，人机分工明确（Q68）。

展开：limitation 要诚实说：大仓库全局性重构仍然弱（上下文装不下全局依赖关系）、长任务漂移（跑偏后越走越远，需要 checkpoint 回顾）、以及生成的代码"看起来对"需要人真正 review——完全无人监督的生产改动还不成熟。这题的满分答法是**结合自己使用体验**讲出 2~3 个"我观察到它为什么好/哪里翻车"的细节——背概念一听就穿。
