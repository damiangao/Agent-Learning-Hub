# 六、评测与可观测（参考答案）

---

**Q95.【P0】 离线评测 vs 在线评测？**
一句话：离线（评测集上跑分）管"变更前把关"——快、可回归、可对比，但分布可能失真；在线（真实用户流量）管"实际效果"——A/B 指标、用户反馈、badcase 回流，但慢、贵、有风险。上线前靠离线，上线后靠在线，badcase 反哺离线集，闭环。

展开：分工：离线回答"这个版本比上个版本好吗"（回归），在线回答"用户真的满意吗"（效果）。

用吃饭打比方：离线评测 = 餐厅新菜上市前让固定试吃员尝——便宜、快、能反复对比，但试吃员口味不代表所有客人；在线评测 = 真实客人点了这道菜的回头率和差评率——数据真实，但等你发现难吃，已经有一批客人流失了。

只做离线的坑：评测集过时（试吃员吃惯了你家口味）、刷分（过拟合评测集）；只做在线的坑：把用户当测试小白鼠，事故直接发生在线上。所以顺序是：离线把关 → 灰度小流量在线验证 → 全量，线上发现的 badcase 回流进离线集，形成闭环。

陷阱：只会背定义不会说闭环是减分。加分点：给出各自典型指标——离线：准确率/格式合规率/faithfulness；在线：任务完成率、点踩率、人工转接率、留存。

**Q96.【P0】 LLM-as-a-Judge 的偏差？**
一句话：用强模型按 rubric 给输出打分，替代人工。已知系统性偏差：位置偏好（对比评测偏爱第一个/某个位置的答案）、长度偏好（偏爱长答案）、自我偏好（偏爱和自己风格/自己生成的答案）、以及 rubric 外漂移（评分不稳定）。

展开：为什么还是主流：人工标注一条可能要几块钱、几分钟，judge 一条几分钱、几秒钟，而且可以无限重复、随时重跑。代价是 judge 不是天平，是一把有系统误差的尺子。

三种偏差怎么理解：

1. **位置偏好**：你让 judge 回答"A 和 B 哪个答案更好"，它有统计上显著的倾向选某一个位置（比如第一个）。类比：评委连续品菜，第二道总觉得不如第一道鲜。对策见下。
2. **长度偏好**：judge 倾向给长答案高分——因为长答案"看起来更努力"。被评系统会学到这一点，越写越长，分数涨了，用户体验反而降了。
3. **自我偏好**：GPT 系模型当 judge 会偏爱 GPT 风格的回答。类比：裁判偏袒和自己一个俱乐部的选手。

用对的前提：

1. rubric 具体可判："答案是否包含正确订单号"而不是"答案好不好"——模糊 rubric 会让 judge 自由发挥；
2. 对比评测时**交换位置跑两次**，两次都赢才算赢，直接消除位置偏差；
3. 用和被评模型不同家的模型当 judge，减少自我偏好；
4. 定期抽样人工校准（Q97）。

陷阱：只背偏差名字、说不出对策，面试官会追问"那你怎么办"。一句加分话："judge 是仪器，仪器要校准，不校准的 judge 产出的是带系统误差的假数据。"

**Q97.【P1】 怎么校准 judge？**
一句话：抽 100~200 条做人工标注金标准 → 算 judge 与人的一致率（如准确率/Cohen's Kappa）→ 低于阈值（如 Kappa < 0.6）就改 rubric / 加 few-shot 评分示例 / 换 judge 模型 → 迭代到可信后再大规模使用；上线后定期重校（模型或 rubric 变更时）。

展开：把流程拆开看，就像**校准体温计**：先拿一盆确定温度的水（人工标注的金标准），看体温计读数差多少（一致率），差太多就调刻度（改 rubric）或换体温计（换 judge 模型）。

实操细节：

1. 金标准怎么来：从评测集抽 100~200 条（覆盖各难度和类别），由人来标注"正确答案"；
2. 算一致率：judge 打的分和人打的分对得上多少。为什么用 Kappa 不用简单百分比见 Q105——简单一致率会被"碰巧一致"虚增；
3. **分歧样本是金矿**——逐条看 judge 和人为什么分歧，通常是 rubric 有歧义（"相关性"没定义清楚），把仲裁结论写成 few-shot 例子喂给 judge，一致率通常显著上升；
4. 分指标校准：judge 判"格式对错"可能和人 95% 一致，判"有用性"可能只有 70%——对低一致性的维度降权，或这个维度直接改用人工，而不是整个 judge 一刀切扔掉。

陷阱：说不出"分歧样本怎么用"，校准就成了空话。

**Q98.【P0】 Golden set 怎么建、怎么维护？**
一句话：建：从真实流量 + 历史坏例 + 边界构造中攒 200~1000 条，每条带标注答案/判分标准，版本化管理；维护：固定评审节奏（如每月）、新 badcase 持续入库、定期淘汰不再代表业务的旧样本；分歧：双人背靠背标注，不一致的仲裁并回写标注规范。

展开：来源怎么理解——

- **真实流量**：抽样真实用户输入，保证分布不失真（这是评测集的生命线）；
- **历史坏例**：出过事故的 case 优先入库，防止"同一个坑摔两次"；
- **边界构造**：手写极端输入（超长 query、空检索结果、带注入的输入），测系统下限。

关键心法：golden set 是"尺子"，尺子本身要稳。类比：你用一把会自己变长的尺子量身高，所有"长高"的结论都不可信。所以样本变更要记录 changelog——这次改了 50 条，指标波动多少归因于尺子（评测集变了）、多少归因于代码（系统真变了），必须能分开说。

防过拟合的结构：核心集（不大动，做回归，像每学期的必修统考）+ 漂浮集（定期换新，防刷分，像随堂测验）。

加分点：说"标注规范和代码一样要 code review，标注分歧率是规范质量的指标"。

**Q99.【P0】 模型指标好但业务指标不动？**
一句话：三种典型原因：① 评测集和真实分布脱节（刷分了）；② 优化的是代理指标不是用户价值（格式合规率涨了，但用户要的是答得对）；③ 业务侧瓶颈不在模型质量（入口流量、交互设计、响应速度）。定位：拉齐分布（评测集换新样本）→ 按用户分群看在线指标 → 找"离线涨了在线没涨"的具体 case 对比分析。

展开：这是 open-ended 题，考排查思路。三种原因分别对应"尺子歪了、目标和价值脱节、你修的不是坏掉的地方"。

经典案例帮你看懂什么叫"瓶颈不在模型"：RAG 准确率从 85% → 92%，客服点踩率却没变。分析发现点踩的用户全是问"我的订单什么时候发货"——这种问题要调订单 API 才能答，知识库答得再好也接不住。点踩率的瓶颈是**能力覆盖**，不是质量。优化准确率这一刀，砍在了不疼的地方。

排查顺序（也是答题顺序）：

1. 先怀疑尺子：评测集是不是旧样本、和线上分布脱节了；
2. 再分群看：整体指标不动，是不是"新用户变好了、老用户变差了"互相抵消；
3. 最后逐 case 对比：找"离线分数涨了、在线体验没变"的具体输入，看它在线上实际是怎么被处理、有没有走到优化过的路径。

教训：指标要和"用户任务能否完成"挂钩（任务完成率 > 文本相似度）。能讲一个自己版本的这类故事，非常加分。

**Q100.【P1】 LLM 功能的 A/B 怎么做？**
一句话：和传统 A/B 相同的骨架（随机分流、足够样本量、统计显著性），不同在三处：① 噪声大——同一输入输出都随机，指标要按会话/用户聚合而非按请求；② 指标模糊——主观满意度要靠代理（完成率、点踩率、重试率、人工转接率）；③ 护栏指标必设——新版本效果涨了但成本/延迟/P0 事故率不能涨。

展开：骨架不用重学：把用户随机分成两组，一组用旧版、一组用新版，比指标。三个不同点展开：

1. **为什么按用户聚合**：LLM 同一个问两次答案都不同，"按请求"统计时噪声大到真实差异被淹没。按用户聚合（一个用户所有请求的平均分算一个样本点）相当于先在组内求平均再比，方差小得多。
2. **为什么靠代理指标**：满意度没法直接量化，就用用户行为当投票——重试一次 ≈ 变相点踩，中途放弃 ≈ 不满意，转人工 ≈ 彻底失败。这些都是现成的日志事件，不用额外埋点。
3. **为什么护栏指标**：LLM 变更的风险不只是效果差，还有成本爆炸（新 prompt 长了一倍）和延迟上升（换了更大模型）。效果指标涨 2%、成本涨 50%，这就是失败的实验。

样本量意识（加分重点）：点踩率从 5% 降到 4%（相对提升 20%）在基率低时需要巨大流量才能统计显著——小流量产品别硬等 A/B 显著，用"离线评测 + 小流量人工评估"过渡。

加分点：分层看效果（新用户 vs 老用户、简单 vs 复杂 query），新版本经常是"复杂 case 变好、简单 case 变差"，整体均值掩盖一切。

**Q101.【P1】 评测怎么接进 CI/CD？**
一句话：把评测集跑分做成 CI 的一个 stage：prompt/模型/检索参数的 PR 触发自动评测 → 关键指标低于基线或显著回退则 block 合并 → 评测报告（分数 + 与上版 diff + 坏例样例）贴在 PR 评论里。

展开：类比单测就懂了：传统代码改了跑 `pytest`，LLM 系统改了 prompt 就等于改了"代码"，凭什么不跑测试？评测就是 LLM 工程的单测。

和单测的三个差别要讲清：

1. **慢且贵**（每次评测是真实的 LLM 调用）：对策是分级——PR 早期跑快照子集（几十条，几秒钟出结果），合并前跑全量集；
2. **概率性**：分数有天然波动，设容忍带（波动 ±1% 内放行）而不是零容忍，否则 CI 红绿乱跳，大家开始无视红灯，评测就形同虚设；
3. **基线管理**：main 分支的最近分数是基线，每次合并后基线自动前移；模型升级时基线要重新定，否则"和旧模型的分数比"没有意义。

陷阱：只会说"接个 CI"不讲差异，面试官会认为你没真做过。这是"把 LLM 工程当软件工程做"的最直接体现，2026 面试高频。

**Q102.【P1】 幻觉自动检测方法？**
一句话：三类：① 引用溯源——生成的每个论断必须能对应到检索片段，对不上就是幻觉（最实用）；② faithfulness judge——让另一个模型逐句判断"该句是否被给定上下文支持"（RAG 三角：query、context、answer 两两评）；③ 自一致性/置信度——多次采样答案矛盾、或 token 级 logprob 异常低，标记可疑。

展开：三类方法逐一拆开：

1. **引用溯源（工程首选）**：架构上强制答案带引用编号，程序校验两点——引用的片段真实存在；该片段确实支持这句话（支持性可用 NLI 模型或小 LLM 判）。类比学术论文：论断没有出处，审稿人直接打回。校不过的答案降级为"根据资料未能找到"——宁可不答，不编。
2. **faithfulness judge**：无引用的输出用另一个模型当质检员，逐句问"这句话能从给定上下文推出来吗"。RAG 三角就是三条边各评一次：答案对上下文忠实吗（faithfulness）、答案切题吗（relevance）、检索的上下文切题吗（context relevance）。
3. **自一致性/置信度**：同一个问题采样 5 次，答案互相矛盾说明模型自己也不确定（类比：开卷考同一个学生三次，三次答案不同，说明他根本不会，是蒙的）。logprob 异常低同理——模型对自己说的话没信心。

陷阱：检测的位置要说清——生成后拦截（保住单次输出的底线）+ 评测集里持续监控幻觉率（看版本趋势），两手都要有，只说方法不说放在哪是半分。

**Q103.【P1】 上游模型升级导致漂移怎么办？**
一句话：发现：固定"哨兵评测集"每天定时跑，分数异常告警（供应商可能已静默换模型）；输出指纹监控（输出长度分布、格式合规率突变也是信号）。应对：prompt/参数重跑评测集定位回退点 → 定向修 prompt → 重大回退则切版本锁定的旧模型（API 的 snapshot 版本或自托管）→ 给供应商提工单。

展开：这题的深层考点：你是否把"模型"当成**会突变的依赖**来管理。

类比：你依赖的第三方库某天在你不知情的情况下自动升级了，接口没变但行为变了，你的功能悄悄坏了。上游 LLM API 就是这样一个依赖，而且供应商**没有义务通知你**（同一个型号名，权重可能已静默更新）。

哨兵评测集怎么理解：从 golden set 里挑一小撮最敏感的 case（比如 50 条对格式、拒答边界最挑剔的），每天定时跑一遍打分。正常波动在容忍带内；供应商换了模型，分数会突然系统性偏移——这就是你的"烟雾报警器"。输出指纹是廉价的补充信号：输出平均长度从 300 token 突变到 800、格式合规率从 99% 掉到 85%，都可能是底层模型变了。

应对按伤害最小顺序：先定位（重跑全量评测集，看哪些指标回退、回退到哪个能力上）→ 定向修 prompt（多数漂移这样解决）→ 修不动就切版本锁定的旧模型兜底（这就是为什么生产必须锁版本）→ 同时给供应商提工单要说法。

预防优于发现：生产系统**锁版本**（用带日期的模型版本号而不是 "latest"），升级当成一次变更走完整评测流程。答出"哨兵集 + 版本锁定"两个词就到位。

**Q104.【P1】 Tracing 工具记录什么？**
一句话：一次调用的完整谱系：trace（一次任务）→ span 层级（检索 span、LLM span、工具 span），每个 LLM span 记：模型/版本、完整输入消息、输出、token 用量、延迟、成本、错误；检索 span 记：改写后的 query、召回列表与分数；工具 span 记：调用参数、结果摘要、耗时。

展开：层级结构用类比：trace = 一整次问诊（挂号到离开），span = 里面的每一步（抽血、拍片、开药）。一个 agent 任务里"检索 → 调 LLM → 调工具"各自是一个 span，挂在同一个 trace 下，有先后和嵌套关系。

为什么要分 span 而不是记一坨日志：坏例排查时你要回答"慢在哪/错在哪"——分了 span 才能说"这次慢是因为检索用了 4 秒"、"答错是因为召回列表里根本没有正确文档"，而不是笼统的"这次失败了"。

工具选型顺口：LangSmith（配 LangChain 生态顺）、LangFuse（开源可自托管，国内合规友好）、或 OpenTelemetry 自建（大厂统一观测栈）。

价值不在记录在**用法**：按坏例过滤 trace、对比同一输入两次执行的差异（为什么这次没召回？）、统计各环节延迟/成本分布（钱花在哪一步）。加分点："trace 的终极消费者是评测——每条线上 badcase 一键转成评测用例。"

**Q105.【P1】 人工标注的质检和一致性？**
一句话：规范先行（可操作的正反例文档）→ 双人背靠背标 → 不一致率监控 + 分歧仲裁（第三人/讨论）→ 一致性量化（Cohen's Kappa）→ 分歧案例回流修订规范 → 标注员定期校准测试。

展开：流程逐环节说清为什么：

1. **规范先行**：标注员是按规范打分的人，规范模糊则一切白干。"相关""高质量"必须换成可判定判据（"包含答案所需的具体数字/步骤"）；
2. **双人背靠背**：同一批数据两个人独立标，互相不看对方结果。不一致就暴露了规范的歧义点——不一致本身是信息，不是麻烦；
3. **仲裁**：第三人或集体讨论裁决分歧，结论回写进规范（这次为什么算"相关"，写成新例子）；
4. **量化一致性**：用 Kappa 而不是简单一致率，因为要剔除"碰巧一致"：两个标注员各 90% 都标"是"，纯靠瞎猜也能有约 81% 的一致率，Kappa 把这部分扣除。经验值：Kappa < 0.4 说明规范有问题，先修规范别急着用数据；
5. **校准测试**：标注员定期做小测（带已知答案的样本），防止时间长了各自"风格漂移"。

实操坑：标注员对业务熟不熟直接影响质量——给上下文文档。加分点：说"LLM 预标注 + 人工复核"能提效 2~3 倍，但要抽检 LLM 标注质量防止系统性带偏（judge 的偏差问题在 Q96 同样适用于预标注）。

**Q106.【P1】 组件级评测为什么必要？**
一句话：端到端只给一个总分，坏了不知道坏在哪——把 RAG 拆成检索（recall/MRR）和生成（faithfulness/答案正确率）分别评，才能定位"检索没召回"还是"召回了对但没答好"，优化才有靶子。端到端的盲区：组件误差互相抵消或互相放大，总分看不出。

展开：类比体检：端到端指标 = "你感觉怎么样"（"还行"），组件级评测 = 血常规分项。发烧了只说"感觉不行"，医生没法开药；分项一查是白细胞高——感染，药就有了。

RAG 拆成两段各自评：

- **检索侧**：正确文档有没有被召回、排得靠不靠前（recall@k、MRR）；
- **生成侧**：给定了正确文档，答案答对了吗、忠于原文吗（正确率、faithfulness）。

典型场景：端到端准确率 70% 长期不动，一拆发现检索 recall@5 已经 95% 但生成正确率只有 73%——文档都给到嘴边了还是答错，瓶颈在生成侧，改 prompt/换模型，而不是继续调检索参数。反过来（检索只有 60%、生成 98%）就是去调 chunking 和检索，prompt 一个字不用动。

扩展到 agent：工具调用准确率、规划质量、终止合理性都是可拆的组件指标。这题和 Q41（排障二分法）是同一种思维的评价面，一起答。

**Q107.【P0】 用户反馈闭环怎么设计？**
一句话：采集（显式：点赞点踩、修正；隐式：重试、改写再问、中途放弃、转人工）→ 归因（badcase 自动分类：检索没中/答错/格式问题/超范围）→ 入库（badcase 进评测集 + 优先级队列）→ 修复 → 带着修复版本回归验证 → （可选）通知用户"你反馈的问题已改进"。

展开：逐环节要点：

1. **采集**：隐式信号常比显式更有信息量——点踩要用户动一下手，而重试、改写再问、中途放弃是用户用脚投的票，日志里现成就有，覆盖面大得多。用户重问一次 ≈ 变相点踩。
2. **归因**：坏例要分类才能修——"检索没中"去调检索，"格式错"去改 prompt，归因错了修复就白干。归因可以先用 LLM 预分类 + 人工抽检。
3. **入库**：badcase 进评测集（防止复发，Q98 的"历史坏例"来源）+ 进优先级队列。
4. **修复 → 回归验证**：改完用包含这个 badcase 的评测集重跑，确认修好且没修坏别处。

工程关键：反馈必须带完整上下文快照（当时的 trace，Q104），否则事后无法复现归因——"用户点踩了，但我们不知道当时检索了什么"，这个反馈就废了。

优先级：高频 × 严重的坏例先修——反馈闭环也是需求排序的依据。加分点：给闭环一个指标——"badcase 复发率"（修复后同类问题是否再出现），衡量闭环是否真转起来了。

**Q108.【P2】 评测集太大跑不起，怎么 sampling？**
一句话：分层抽样保分布（按类目/难度/语言分层，每层按比例抽）；核心集 + 随机浮动集（核心防回归、浮动防过拟合）；变更感知采样——改动只影响某类功能时优先跑相关子集；定期全量（如每周）兜底。

展开：四个手段各一句话：

1. **分层抽样**：不是随机抽 500 条，而是"1 万条里每个类目按比例各抽"——否则小类目可能一条都抽不到，恰好是小类目回退了你也不知道；
2. **核心 + 浮动**（同 Q98 的结构）：核心集每次必跑保回归，浮动集换着跑防刷分；
3. **变更感知采样**：这次 PR 只改了"订单查询"工具的 prompt，那就优先跑工具类子集——把评测预算花在改动的影响面上；
4. **定期全量兜底**：抽样省下的成本，每周花一次全量把漏网之鱼捞回来。

先算清楚再优化：单条成本 × 全量 = 每次回归花费，如果全量只要几块钱，别优化，直接全量。真正的成本大头通常是端到端 agent 评测（每个 case 跑几十轮工具调用）——这时优化的是 case 的代表性而不是跑得快。

**Q109.【P2】 公开 benchmark 为什么不能说明你的应用好？**
一句话：三个错位：分布错位（MMLU 考学科知识，你的场景是客服工单）、任务错位（它考模型能力，你考"模型+RAG+prompt+工具"的系统效果）、判分错位（它有标准答案，你的"好"是业务定义的）。模型榜是选型的初筛信号，系统好不好只能用自己的评测集回答。

展开：三个错位展开：

1. **分布错位**：评测集的题和你的用户输入不是一种东西。MMLU 是选择题、学科知识；你的线上是病句、错别字、五句话挤一行的客服工单。模型考北大，你的用户说的是方言。
2. **任务错位**：榜单测的是裸模型；你线上跑的是"模型 + RAG + prompt + 工具"整个系统。裸模型排行榜第一的系统，可能检索组件一塌糊涂。
3. **判分错位**：榜单有标准答案；你的"好"是业务定义的（客诉 resolved、用户没再问第二次），没有唯一标准答案，只能用自己的判分标准。

正确的使用姿势：公开榜做**粗筛**（从 100 个候选缩到 5 个，省你自评的成本）+ 泄露风险意识（榜单题可能进了训练数据，分数虚高——相当于考原题）+ 真正决策依据自己建的 golden set（Q98）。

一句总结加分："你的评测集就是你的 benchmark——它是唯一和你的分布一致的。"
